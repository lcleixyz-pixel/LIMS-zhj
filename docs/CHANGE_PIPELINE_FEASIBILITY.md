# 外部规范变更 → 内部文件链路：可行性论证与五层方案

> 结论先行：「响应式自动变更文件」不可行也不合规；重构为「基于块级追溯图的**事件驱动变更管理流水线**」后完全可行，且现有数据模型已完成大半基础。
> 配套：[EXPERT_AGENT_ROADMAP.md](EXPERT_AGENT_ROADMAP.md)、[EXPERT_AGENT_TASKS.md](EXPERT_AGENT_TASKS.md)、[QMS_TRACEABILITY_DATA_MODEL.md](QMS_TRACEABILITY_DATA_MODEL.md)

## 一、需求还原

原始诉求：外部规范性文件（ISO 17025、CNAS-CL01/G001/A015、CMA 2023 评审准则、珠宝检测方法标准 GB/T 等）发生变更时，系统能响应式地调整本所结构化文件，并维持「条款 → 质量手册章节 → 程序文件 → 作业指导书 → 记录表格字段」的逐级文件链路。

## 二、分层可行性判断

| # | 能力 | 可行性 | 依据 |
|---|------|--------|------|
| ① | 逐级文件链路（块级双向追溯图） | **高，基础已具备** | 确定性图结构问题。已有 `qms_clauses` / `qms_element_clause_links` / `qms_document_blocks` / `qms_document_block_links`；记录表格到程序文件块的正式关系应落在 `qms_document_block_links.record_form_template_id` + `relation_type=requires_record`，`record_form_templates.procedure_doc_id` 仅作文件级归属/兜底查询。`qms_reference_procedure_matches` 已可复用；AI 候选链接建议新增专表 `qms_block_link_suggestions`，避免把结构化候选塞进通用 `qms_agent_suggestions.evidence` |
| ② | 变更影响分析 | **高** | 链路建至块级后，影响分析 = 图遍历，结果确定可穷举；AI 仅负责新旧条款 diff 的语义解读 |
| ③ | 自动感知外部变更 | **低-中** | 无结构化数据源：CNAS/市监总局仅发公告与 PDF，标准原文有版权、无机读 diff。可行下限 = 监测公告清单、登记变更事件；不可行 = 自动抓取解析标准全文 |
| ④ | 全自动响应式修订 | **不可行，且不应做** | 17025 条款 8.3 要求文件修订经授权人员审查批准——全自动改文件是不合规设计；条款变更对本所的影响判定（现行做法是否仍符合）是人的决策点 |

## 三、变更频率校准（决定投入方向）

| 变更源 | 实际频率 | 对策 |
|--------|----------|------|
| ISO 17025 | 约 12 年一版（上次 2017） | 罕见事件，人工主导 |
| CNAS-CL01/G001/A015 | 数年一动 | 事件登记即可 |
| CMA 评审准则 | 2023 刚换版 | 同上 |
| **检测方法标准（GB/T 16552/16553/16554 及配套方法标准）** | **每年可遇** | **流水线主用例**：换版触发方法验证 + 作业指导书修订 + 记录表格调整 + 人员培训确认，CNAS 有明确程序要求 |

推论：为十年一遇的管理体系标准换版建重自动化，ROI 为负；围绕**方法标准换版**设计流水线，每年还本。

## 四、五层方案（事件驱动变更管理流水线）

成熟先例：系统工程的需求追溯管理（DOORS 模式）——外部条款 = 结构化需求库，内部文件块与需求建立 satisfies 链接，变更 = 需求库版本升级 → 失配检测。

```text
L1 追溯图         条款/标准要求 ←→ 文件块 双向链接（AI 预匹配 + 人批量确认）——一次性投入
L2 感知           脚本监测 CNAS/SAMR/标准平台公告 → 人工登记 qms_external_change_events（新旧版本文件由人提供）——月度节拍
L3 影响分析       新旧条款 diff（AI）→ TraceGraphService 遍历 L1（确定性）→ 影响清单 + 变更评估报告
L4 修订执行       AI 起草 redline → 人审 → 8.3 审批 → 版本升级 → 分发/回收（= 现有文件控制流程被 AI 加速）
L5 闭环验证       修订完成后重跑失配检测，确认图上无悬空引用、无残留失配
```

| 层 | 定位 | 验收要点 |
|----|------|----------|
| L1 | 全流水线的前置与最大单项投入 | 枚举清单内程序文件块级建链 100%；AI 预匹配采纳率有统计；链接双向可查询 |
| L2 | 触发器是「登记的事件」而非「自动监听」 | 变更事件有唯一登记入口 `qms_external_change_events`，至少记录来源、文号、新旧版本号、新旧依据 ID、发布日期、生效日期、附件、状态、图快照 hash；公告监测漏报靠月度人工兜底 |
| L3 | 缺口扫描与变更影响抽出同一个 `TraceGraphService`：缺口 = 从未满足；变更 = 曾满足现失配 | 影响清单可复算（同一事件 + 同一图快照 hash 输出一致）；报告含条款 diff 摘要、受影响文件块清单、建议动作 |
| L4 | AI 只加速不替代：草稿 + 人批 | 修订全部走 8.3 审批流；redline 可与原文逐段对照 |
| L5 | 防「改了一半」 | 事件关闭条件 = 失配数归零或余项显式豁免（附理由） |

与原设想的本质区别：牺牲「全自动响应」这个不合规也不可靠的部分，保留全部实际价值——从公告发布到全套受控文件完成修订，周期从数月压缩到数天。

## 五、结论与对任务单的影响

1. 需求**重述后完全可行**；体系策划中心与结构化文档表就是 L1 的正确地基，方向未走错。
2. 最大单项投入是块级建链：约 38 份程序文件 × 每份十余块 ≈ 数百条链接，AI 预匹配 + 人确认，工时可控。
3. 任务单变更（已同步 [EXPERT_AGENT_TASKS.md](EXPERT_AGENT_TASKS.md)）：
   - T2.5 升级为 L3 的特例（缺口检测），与变更影响分析共同抽出 `TraceGraphService`；
   - 新增 T2.6（L1 块级建链）、T2.7（L2 变更事件登记与公告监测）、T2.8（L3 变更影响分析 + L5 闭环）；
   - T2.2 增补 L4「redline 修订模式」要求。
4. 风险提示：L1 建链质量决定 L3 上限（漏链 = 漏报影响），建链验收必须含人工抽检；方法标准原文获取与版权处理同标准卡片库约束（要点复述，不整篇收录）。
