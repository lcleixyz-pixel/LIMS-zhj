# 活动级责任链界面整治设计

- 版本：v0.1
- 日期：2026-07-14
- 状态：已确认设计，待书面规格复核
- 适用模块：`/planning/responsibilities`

## 1. 目标

将活动级责任链从“开发数据展示页”调整为普通质量管理人员可直接使用的业务页面。使用者无需理解数据库状态值、岗位代码、哈希或 UUID，也能判断：当前处于哪一步、还缺什么、下一步应做什么。

本轮只调整责任链模块的文案、信息层级、页面布局和交互提示。现有责任链业务规则、权限、签批、事务、审计、数据库结构和文件对齐算法保持不变。

## 2. 已确认问题

1. 页面直接显示 `draft`、`effective`、`warning`、`blocker`、`approved` 等内部状态值。
2. `core_governance`、`internal_audit`、`named_person`、岗位代码、职责环节代码等开发标识占据主要视线。
3. `content_hash`、`baseline_hash`、UUID 和原始 JSON 被当作普通业务信息展示。
4. 责任结构、人员配置、校验签批、有效责任链和文件对齐五个入口平铺，缺少主流程与辅助工具的区分。
5. 人员配置表单只有一排控件，字段含义、必填关系和保存后果不够清晰。
6. “运行时指定”“草案预览”“门禁”等术语缺少面向使用者的解释。
7. 校验结果只显示机器状态，没有明确告诉用户哪些是提醒、哪些会阻止提交。

## 3. 采用方案

采用“中文化 + 四步流程引导 + 技术信息渐进披露”。保留 Bootstrap、ThinkPHP 服务端模板和现有全局导航，不引入新框架或第三方前端依赖。

主流程固定为：

1. 定义职责；
2. 配置人员；
3. 校验并签批；
4. 查看已生效责任链。

“文件对齐”属于辅助检查，不占用主流程步骤，放在页头工具区或独立辅助入口。

## 4. 页面信息结构

### 4.1 页头

- 标题使用“责任链”。
- 副标题说明本页管理“活动—岗位—职责—人员”。
- 显示版本号、中文状态和未配置岗位数量。
- `chain_code` 不在主界面显示；必要时进入“技术详情”查看。
- 有效版本的“复制为修订草案”保留，但与只读工具分开。

### 4.2 流程导航

- 用四步流程导航替代五个等权页签。
- 当前步骤明显高亮，已完成步骤与未完成步骤有不同状态。
- 每一步显示一句业务解释，例如“先确认职责结构，不需要立即选人”。
- “文件对齐”显示为次级按钮，并注明“只读检查”。

### 4.3 责任结构

- 顶部显示活动数、职责数、需预先指定人数的职责数、在具体活动中确定的职责数。
- 按内部审核、管理评审、风险管理分组。
- 职责类型、岗位角色全部中文化。
- 环节代码和岗位代码移入每条职责的“技术详情”。
- “运行时指定”改为“在具体活动中确定”，并直接说明由谁、在何时确定。

### 4.4 人员配置

- 先分成“需提前指定具体人员”和“在具体活动中确定责任人”两类。
- 后一类只展示规则说明，不显示不可操作的人员表单。
- 固定岗位表单使用明确标签：具体人员、适用场所、拟生效日期、能力证据、资格证书。
- 说明“保存后仍是草案，不构成任命”。
- 已绑定人员显示中文状态；移除按钮只在草案状态出现。

### 4.5 校验与签批

- 将操作分为三段：检查责任结构、检查签批条件、提交签批。
- 清楚说明前两项是检查，第三项会锁定版本并进入签批。
- 校验结果中文化为“可以继续”“需要补充”“暂不能提交”。
- 问题严重度中文化为“提醒”“阻断”。
- 内容哈希、批次键和版本哈希放进“技术校验信息”折叠区。
- 公司总经理身份证据和实验室主任首次任命保留独立治理区，避免与日常职责签批混在一起。

### 4.6 已生效责任链

- 主表只展示人员、岗位、职责、场所、有效期和依据状态。
- 责任链版本 UUID、签批 UUID 等放进逐行“证据详情”。
- 空状态说明下一步应先完成配置和签批，不只显示“暂无记录”。

### 4.7 文件对齐

- 标题改为“体系文件职责一致性检查”。
- `conflict`、`review_required` 等状态显示中文。
- 主表聚焦：发现项、结论、文件写法、责任链写法、建议处理方向。
- 代码、哈希、JSON、来源责任项 ID 收入“核验依据”折叠区。
- 草案检查明确标注“仅预览，不作为现行责任依据”。

## 5. 中文映射规则

### 5.1 版本与任命状态

| 内部值 | 页面显示 |
|---|---|
| `draft` | 草案 |
| `pending_approval` | 待签批 |
| `effective` | 已生效 |
| `superseded` | 已被新版本替代 |
| `revoked` | 已撤销 |
| `active` | 有效 |
| `expired` | 已到期 |

### 5.2 校验和对齐状态

| 内部值 | 页面显示 |
|---|---|
| `pass` | 可以继续 |
| `warning` | 需要补充 |
| `blocker` | 暂不能提交 |
| `conflict` | 存在冲突 |
| `review_required` | 需要人工确认 |
| `aligned` | 一致 |

### 5.3 职责类型

| 内部值 | 页面显示 |
|---|---|
| `organize` | 组织 |
| `review` | 审核 |
| `approve` | 批准 |
| `execute` | 执行 |
| `verify` | 验证 |
| `record_keep` | 记录与归档 |
| `countersign` | 会签 |
| `inform` | 提供信息 |

### 5.4 人员确定方式

| 内部值 | 页面显示 |
|---|---|
| `named_person` | 需提前指定具体人员 |
| `activity_instance` | 在具体活动开始时指定 |
| `derived_from_scope` | 根据活动范围自动确定后人工核对 |

内部值仍保留在数据属性、请求参数和数据库中，不修改业务接口。

## 6. 视觉与交互规范

- 所有样式使用 `.qms-responsibility-*` 作用域，避免影响旧页面。
- 沿用全站深蓝主色和冷灰背景，不新增渐变、插画或装饰性动效。
- 流程步骤、状态提示、表单和证据详情采用一致的间距与层级。
- 主要操作每个页面最多一个实心主按钮；检查、返回、只读工具使用次级样式。
- 提供清晰的键盘焦点状态；折叠区使用原生 `details/summary`。
- 移动端允许流程横向滚动，表格继续使用响应式容器。

## 7. 实现边界

预计修改：

- `jewelry-qms/app/controller/PlanningResponsibility.php`：只增加展示用中文映射和页面摘要，不改变业务判断。
- `jewelry-qms/app/view/planning_responsibility/index.html`：重排信息结构和文案。
- `jewelry-qms/public/static/css/qms-responsibility.css`：新增模块专属样式。
- `jewelry-qms/app/view/layout/main.html`：加载模块专属样式文件。
- `jewelry-qms/tests/qms_responsibility_ui_smoke.php`：增加中文化、技术信息折叠和主流程结构断言。

明确不改：

- 数据库表和迁移；
- 责任链职责模板及 3 项活动、21 项职责；
- 人员资格、禁止自批、签批批次和生效逻辑；
- RBAC、审计日志和事务边界；
- 手册—程序对齐算法及判定结果；
- 其他模块的页面风格。

## 8. 测试策略

按测试驱动实施：

1. 先在 `qms_responsibility_ui_smoke.php` 增加断言并确认失败；
2. 断言主界面具备四步流程、中文状态、中文职责类型、下一步提示和技术详情折叠；
3. 断言原始状态、哈希和内部代码不再作为主要可见文本直接输出；
4. 用最小改动使测试通过；
5. 复跑责任链 9 项测试、导航/RBAC 相邻测试和 PHP 语法检查；
6. 在隔离数据库渲染草案、待签批、已生效和文件对齐四种状态，检查页面无模板异常；
7. 合并到本机 8010 前保留数据库快照，并进行登录后的浏览器人工验收。

## 9. 验收标准

1. 责任链主要页面不再直接暴露英文状态值、哈希名称、UUID 和原始 JSON。
2. 用户能从顶部流程判断当前阶段和下一步操作。
3. 用户能区分“需提前指定人员”和“具体活动中再确定人员”。
4. 校验结果能明确区分提醒与阻断。
5. 技术人员仍可通过折叠详情核对内部代码、哈希和追溯 ID。
6. 责任链既有业务测试全部通过，数据库结构与业务逻辑无变化。
7. 其他模块页面无视觉或行为变化。

## 10. 回退方式

本轮是模板、展示数据和模块 CSS 的独立提交。若验收不通过，可回退该提交恢复原页面；不需要回滚数据库，也不会影响已形成的责任链草案、签批或任命记录。
