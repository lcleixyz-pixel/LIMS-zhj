# P1-4 内容块连续办理卡设计规格

日期：2026-07-29

状态：用户已确认，进入实施

## 1. 目标

在文件治理工作台增加“按内容块连续办理”区域，把同一内容块上的追溯问题汇总到一张卡片，减少质量员在文件级结论、治理候选、设计链条和追溯复核页之间反复判断。

本次采用方案 A：

- 新增只读汇总卡；
- 保留现有治理候选、系统设计链条、记录字段支撑、冲突提醒和下一步动作；
- 复用现有候选预填链接和追溯复核入口；
- 不新增写接口，不自动保存，不自动拆分关系，不自动判定治理完成。

## 2. 使用者看到什么

区域标题为“按内容块连续办理”，放在文件级结论及自动识别原因之后、现有“治理候选”之前。

标题同时显示：

- 待办理内容块数量；
- 待处理问题总数；
- 中文提示“系统只负责归并和导航，处理结果仍以追溯复核页逐条确认为准”。

每张内容块卡片显示：

1. 内容块章节号和中文名称；
2. 内容块类型的中文说明；
3. 问题标签；
4. “本块要做”中文步骤；
5. 可用候选的来源、编号、名称和建议用途；
6. “处理此内容块”主入口；
7. 候选可用时的“带入此候选”入口。

没有待办理内容块时，显示“当前没有需要汇总办理的内容块”，不渲染空卡片。

## 3. 汇总的问题类型

| 问题代码 | 中文标签 | 判定来源 | 处置提示 |
|---|---|---|---|
| `mixed_relation` | 关系混装 | 既有关系包含多个目标对象 | 先查看拆分预览，逐条新增正确关系，核对后再处理旧关系 |
| `suspected_mismatch` | 疑似错挂 | 语义防错判断当前主链与建议章节不一致 | 先调整错挂关系，再建立建议主链 |
| `pending_review` | 等待复核 | 既有关系尚未人工确认 | 核对来源、用途和对象后逐条确认 |
| `missing_primary` | 缺少主链 | 候选已定向到本内容块，但没有对应的已确认主链 | 使用候选预填进入复核页，人工确认后才计入闭环 |

同一关系只产生一个结构性问题：

1. 关系混装优先于疑似错挂；
2. 疑似错挂优先于等待复核；
3. 已确认主链不再产生等待复核问题。

同一候选对象已经在本内容块形成对应的已确认主链时，不再显示“缺少主链”。

## 4. 内容块归并规则

以 `block_id` 为唯一归并键。

每张卡片的展示模型包括：

```php
[
    'block_id' => '...',
    'section_number' => '5.2',
    'title' => '文件修订',
    'block_type_label' => '控制要求',
    'priority' => 'blocked',
    'issue_count' => 2,
    'issues' => [
        [
            'code' => 'suspected_mismatch',
            'label' => '疑似错挂',
            'message' => '当前手册章节与建议章节不一致。',
        ],
    ],
    'candidates' => [
        [
            'candidate_kind' => 'manual_section',
            'candidate_kind_label' => '手册条款',
            'target_label' => '8.3 文件控制',
            'relation_label' => '主链：落实手册',
            'review_url' => '/planning/structures/links/review?...',
        ],
    ],
    'review_url' => '/planning/structures/links/review?block_id=...',
]
```

优先级及排序：

1. 含关系混装或疑似错挂的卡片为 `blocked`；
2. 仅含等待复核或缺少主链的卡片为 `review`；
3. 先按优先级，再按内容块 `sort_order`，最后按标题稳定排序。

`sort_order` 只作为服务内部排序键，输出展示模型前移除。

只输出至少包含一项问题的内容块。

## 5. 候选复用

继续使用 `QmsTraceCandidateRoutingService` 已生成的：

- `target_block_id`；
- `target_block_title`；
- `relation_type`；
- `relation_label`；
- `review_url`；
- `recommendation_reason`。

候选必须满足 `routable=true` 才能进入内容块卡片。

不可路由候选不生成虚假按钮，仍留在现有治理候选区显示原有阻断原因。

候选按“外部依据、手册条款、运行记录”稳定排序；同一 `kind + target_id + block_id` 只显示一次。

## 6. 中文办理步骤

每张卡片按实际问题生成简短步骤，不使用工程术语：

1. 有关系混装：先“查看拆分预览，逐条建立正确关系”；
2. 有疑似错挂：再“调整当前错挂关系”；
3. 有可用候选：再“带入候选，核对后保存”；
4. 有等待复核：最后“逐条确认仍待复核的关系”。

页面不显示完成复选框，不把进入页面、展开详情或点击链接当作完成。

## 7. 页面布局

- 区域使用单列任务卡，避免在一张卡中横向压缩较长的问题说明。
- 卡片头部显示内容块名称、问题数和最高优先级。
- 问题标签使用现有状态色，不新增动画。
- 主按钮为“处理此内容块”。
- 候选入口为次要按钮“带入此候选”。
- 小于 768 像素时，卡片头部、步骤和按钮纵向排列，按钮占满可用宽度。
- 保留现有 Bootstrap 5 和 `qms.css`，不引入新依赖。

## 8. 服务边界

在 `QmsFileGovernanceWorkbenchService` 中增加纯展示装配，不修改：

- 追溯关系写入规则；
- 候选语义计算；
- 关系状态判断；
- 文件状态机；
- 审批或签署流程；
- 数据库结构。

建议将内容块汇总逻辑放入独立的 `QmsTraceWorkItemService`，公开接口：

```php
public static function build(
    array $blocks,
    array $candidateTrace
): array
```

返回：

```php
[
    'items' => [],
    'block_count' => 0,
    'issue_count' => 0,
]
```

该服务只接收已读取的数据并返回展示模型，便于独立测试和复用。

## 9. 错误与兼容

- 内容块没有 ID 时不生成办理卡，避免不可执行入口。
- 候选缺少目标名称时显示“候选对象信息待补充”，但保留可追溯编号。
- 未知内容块类型显示“内容块”。
- 未知关系状态只作为“等待复核”，不静默视为已确认。
- 候选服务暂不可用时，仍可根据现有关系生成混装、错挂和等待复核卡。
- 页面不依赖 JavaScript 生成卡片或基本导航。

## 10. 验收标准

1. 同一内容块的混装、错挂、待确认和缺主链问题只生成一张卡；
2. 问题数量不重复、不遗漏，严重问题优先显示；
3. 可路由候选进入对应内容块，按钮沿用现有预填 URL；
4. 已确认的同类主链不再显示为缺失；
5. 不可路由候选不生成虚假操作入口；
6. 现有治理候选区、系统设计链条和下一步动作保持可用；
7. 工作台仍不包含写入表单；
8. 桌面与窄屏均无横向溢出；
9. 读取及浏览器验收前后有效追溯关系保持 3182；
10. 不提交任何追溯表单，不写入或改动 8010；
11. P0-1 至 P1-3 相关回归继续通过；
12. 纸质体系仍是唯一正式体系。
