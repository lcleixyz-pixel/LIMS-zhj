## 1. 目标

为真实组织与真实人员建立一个可审核、可预检、可回退、可重复演练的最小迁移包。迁移包只处理组织任命和与其直接相关的数据完整性约束，不处理模拟业务记录、代码合并、云端发布或员工开放。

本设计落实以下管理要求：

- ISO/IEC 17025:2017 5.2、5.5：识别管理层，明确组织结构、职责和权限；
- 6.2.4～6.2.6：传达职责、保留人员授权记录，并限定授权活动；
- 7.11.2～7.11.3：系统变更在实施前授权、文件化、确认并保留完整性和访问控制；
- 8.4：迁移、确认、执行和回退记录可识别、可检索、受保护。

## 6. 清单与防误执行

`00-manifest.json` 至少包含：

- 包版本、生成时间、Git 提交；
- 目标数据库名称；
- 目标公司 ID；
- `PLACE01`、`PLACE02` 的 ID 和名称；
- 迁移前预期计数；
- 受控任命文件编号和生效日期；
- 人工确认单 SHA256；
- 各 SQL 和证据文件 SHA256；
- 允许的执行顺序；
- 明确的 `production_apply_authorized: false` 初始值。

执行器必须同时满足以下条件：

1. 数据库名与命令行显式参数一致；
2. 公司、场所和当前 `admin` 关联指纹与清单一致；
3. 人工确认单 SHA256 与清单一致；
4. 所有文件 SHA256 校验通过；
5. `qms:p0-preflight --format=json` 返回 `blocked=false`；
6. 执行前快照已完成且可读取；
7. 用户另行批准“现行库执行”闸门。

B6 设计、生成和隔离演练不改变 `production_apply_authorized`，也不得绕过第 7 项。

## 7. 执行顺序

### B6-0：冻结输入

- 固定人工确认单、Git 提交和目标数据库指纹；
- 生成 SHA256；
- 确认现行库无 `B5-`、`SIM-` 或验收测试业务记录。

### B6-1：只读预检

- 检查重复业务编号和 CAPA 来源链；
- 检查两场所唯一性；
- 检查人员姓名、编号和活动状态；
- 检查岗位代码唯一性；
- 检查现有任命冲突；
- 检查 `admin` 当前确实指向软删除的张晓磊旧员工行；
- 输出记录 ID 和汇总，不输出联系方式。

任何不一致都以非零状态结束，不进入快照和写入阶段。

### B6-2：升级前快照

- 生成完整数据库快照；
- 单独导出 `employees`、`users`、`qms_positions`、`employee_appointments`；
- 生成快照 SHA256；
- 在隔离库完成一次恢复验证。

未通过恢复验证的快照不得用于现行迁移。

### B6-3：结构完整性

运行 B2 迁移，为投诉、CAPA、不符合和 CAPA 来源链增加四项唯一约束。MySQL DDL 会隐式提交，因此本步骤与组织数据事务分开，并在执行后重新检查四个索引。

### B6-4：组织数据事务

组织数据写入使用单一事务，并锁定目标人员、岗位、场所、账号和任命键：

1. 再次校验人员、编号和场所；
2. 按已确认编号插入两名缺失人员；
3. 按岗位代码补齐三个岗位目录项；
4. 按固定 `appointment_key` 写入 25 项任命；
5. 把 `admin.employee_id` 改指在用张晓磊；
6. 执行事务内断言；
7. 仅在 25 项精确匹配且无额外关系时提交。

现有正式任命若与目标键冲突但内容不同，必须阻断，不允许 `ON DUPLICATE KEY UPDATE` 静默覆盖。

### B6-5：迁移后验收

- 四项唯一约束均存在；
- 两名新增人员姓名、编号和场所正确；
- 25 项任命精确匹配；
- `admin` 指向在用张晓磊；
- 刘恒春没有常设质量负责人任命；
- 没有新增场所；
- 没有模拟业务记录；
- D01～D07、C01～C12、L01～L10、T01～T10、A01～A16 通过；
- 逐岗位页面矩阵在隔离服务通过；
- 迁移差异仅包含清单允许的对象。

## 8. 回退设计

### 8.1 行级回退

`90-row-rollback.sql` 根据 `before-state.json` 固定的 ID 和旧值生成，按反向顺序执行：

1. 恢复 `admin.employee_id`；
2. 撤销本包新建的 25 项任命；
3. 仅当没有任何用户、任命、培训、能力、设备或其他业务引用时，撤销本包新增的两名人员；
4. 仅当没有其他引用且迁移前不存在时，撤销本包新增的岗位目录项；
5. 验证计数和关键字段恢复到迁移前指纹。

回退不得按姓名模糊删除，也不得删除迁移前已存在的人员、岗位或任命。

### 8.2 结构回退

四项唯一约束默认保留，因为它们保护业务数据完整性。`91-schema-rollback-emergency-only.sql` 只在以下条件同时满足时使用：

- 已确认约束导致现有应用不可用；
- 行级回退不足以恢复服务；
- 用户另行批准结构回退；
- 已再次生成快照。

### 8.3 完整恢复

若行级回退无法证明恢复完整性，停止尝试局部修复，使用 B6-2 已验证的完整快照恢复。恢复后重新执行只读预检、计数核对和 `8010` 健康检查。

## 9. 隔离演练

正式申请现行库执行授权前，必须完成：

1. 从现行库只读快照创建隔离克隆；
2. 运行预检；
3. 执行结构迁移和组织数据事务；
4. 完成迁移后验收；
5. 执行行级回退并核对与迁移前一致；
6. 再次迁移，证明包可重复执行且不会重复新增；
7. 从完整快照恢复另一临时库，证明完整恢复路径可用；
8. 销毁临时库和临时账号。

演练证据记录每一步命令、开始/结束时间、退出码、SHA256、计数和结论，但不记录密码。

## 10. 失败处理

| 失败位置 | 处理 |
|---|---|
| 人工确认不完整 | 不生成可执行数据脚本 |
| SHA256 不一致 | 停止，重新冻结包 |
| 只读预检阻断 | 不快照、不写入，回到数据治理 |
| 快照恢复失败 | 不迁移，修复备份链 |
| DDL 失败 | 停止组织数据事务，检查索引和应用兼容性 |
| 数据事务断言失败 | 回滚事务，保留失败证据 |
| 迁移后验收失败 | 首选行级回退；不能证明完整时执行快照恢复 |
| 页面权限回归失败 | 不开放员工登录，不申请云端执行 |

## 11. 验收标准

B6 设计和实现阶段只有在以下条件全部满足时才能申请下一闸门：

- 人工确认单完整但仍由用户最终批准；
- 可执行包无秘密信息且 SHA256 全部通过；
- 克隆库完成“迁移—行级回退—再迁移”；
- 完整快照恢复演练通过；
- 迁移差异与允许清单精确一致；
- P0 回归和逐岗位页面矩阵通过；
- 临时环境已销毁；
- 形成执行记录和版本台账；
- 现行库、`8010` 和云端仍未改变。

下一闸门应单独命名并授权，例如：`G-R13-B7“现行库受控迁移执行”`。批准 B6 不等于批准 B7。
