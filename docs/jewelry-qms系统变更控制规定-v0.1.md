# jewelry-qms 系统变更控制规定（技术备忘）

> 版本：v0.1（技术备忘，**非受控文件**）
> 日期：2026-07-10
> 对应：CNAS-CL01:2018 / GB/T 27025-2019 第 7.11.2 条（变更须批准、形成文件、确认）
> 依据：`.team/当前战役.md` 任务 A4；被 `docs/jewelry-qms计算机化系统验证方案-v0.1.md` 第 8 节引用
> 状态：当前以技术备忘定稿；受控发布排到系统真用稳定之后

## 1. 目的

对应 CL01 7.11.2：实验室信息管理系统的任何变更（含软件配置修改、现成商业软件升级），在实施前都应被**批准、形成文件、确认**。本规定定义 jewelry-qms 的变更怎么管，让每一次改动都可追溯、可验证、可回滚。

## 2. 适用范围

**管**：jewelry-qms 应用代码、数据库结构、配置、依赖与部署环境（Docker 等）的变更。

**不管**（走别的流程）：受控体系文件内容变更（由文控模块管）、日常记录数据录入（日常使用）、记录模板内容调整（文控+模板审查）。

## 3. 角色与职责

| 角色 | 谁 | 干什么 |
|---|---|---|
| 批准者 | 用户（机构拍板人） | 决定改不改、改什么、何时改 |
| 实施者 | AI 副手 / 开发者 | 写代码、跑测试、写记录 |
| 复核 | 用户 | 看变更结果是否符合预期 |

> 一人项目现实：用户既是批准者也是复核。关键是**留痕**——批准和复核写成文字（聊天记录/台账都行），不靠记忆。

## 4. 变更分级（决定管多严）

| 级别 | 例子 | 批准时机 | 测试范围 | 验证方案是否升版 |
|---|---|---|---|---|
| **小** | 错别字、样式、单字段标签调整 | 可事后补记 | 相关 1–2 个冒烟测试 | 否 |
| **中** | bug 修复、加字段、配置改动、新记录模板 | 事前批准 | 相关模块冒烟测试 | 否（台账记） |
| **大** | 新功能模块、数据库结构改、依赖/框架升级、部署架构变 | 事前批准 + 回滚方案 | **全量**冒烟测试 + 真数据回归 | 是（升版本号） |

## 5. 变更流程（六步）

1. **提出**：实施者描述——改什么、为什么、影响哪些功能、定什么级别。
2. **批准**：用户拍板（小改可事后补批，但必须补）。
3. **实施**：在 git 分支上改，不直接动主分支；数据库改走迁移脚本，先在测试库验证。
4. **验证**：按级别跑冒烟测试（`jewelry-qms/tests/*_smoke.php`）；中/大改加真数据功能确认。
5. **记录**：记入 `docs/变更台账.md`（一行：日期/级别/改了啥/谁批/测试结果/版本）。
6. **部署**：合并到主分支、必要时重建容器；大改同步更新验证方案版本表。

## 6. 记录记在哪（三处联动）

- **变更台账**：`docs/变更台账.md` —— 每次变更追加一行，是主索引。
- **验证方案版本表**：`docs/jewelry-qms计算机化系统验证方案-*.md` 第 8 节 —— 大改才更新。
- **运维手册**：`QMS_OPERATIONS_RUNBOOK.md` —— 部署/回滚相关补充。

另有 `CHANGELOG.md` 作为**版本发布汇总**：日常不逐项重复登记，仅在发布新版本号时从变更台账选择对使用者有影响的大项，按主题汇总。

## 7. 红线（不可放松）

- 生产数据库不直接改结构；改走迁移脚本 + 测试库验证 + 用户授权才部署。
- 受控文件变更走文控模块，**不走本规定**。
- 模拟完成不得冒充真实执行（沿用生态红线）。
- **大改必须有回滚方案**（怎么退回上一版），写进台账。
