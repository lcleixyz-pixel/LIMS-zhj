# 手册—程序一致性校验使用说明

- 版本：v0.1
- 日期：2026-07-13
- 适用范围：质量手册第四版与 `CX-08/19/20/21/32` 五份程序的只读试点

## 一、用途与边界

本工具沿系统已有的“手册块—要素—程序文件”追溯关系，检查版本化要求清单与当前程序导出是否一致，并输出可复核的 JSON、CSV 和 Markdown 报告。

本版只完成确定性规则试点，不是对全部手册条款的通用语义审查器。手册修订后，需要先把拟检查的要求整理为试点 JSON 中的原子要求，再由工具定位程序并执行规则。后续可在此输入契约上增加更多规则，但不能把关键词命中直接当作定案。

运行边界：

- 只读取手册、程序 Markdown 和现有追溯表。
- 只向指定报告目录写入结果。
- 不提供 `--apply`，不修改手册、程序、追溯关系或生产数据库。
- `knowledge/internal/` 是生成导出层，只能读取，不能手工整改。

## 二、试点输入

- 要求清单：`docs/qms_manual_procedure_alignment_pilot-v0.1.json`
- 手册：`../knowledge/internal/manual/XZTC_SC-质量手册_第四版.md`
- 程序目录：`../knowledge/internal/procedures/`
- 试点程序：`CX-08、CX-19、CX-20、CX-21、CX-32`

要求清单必须明确：发现编号、手册章节、规则类型、期望值、兜底程序和修订方向。输入文件及其 SHA-256 会写入报告，防止不同版本证据混用。

## 三、运行方式

在已具备项目 PHP 依赖和数据库连接的应用环境中执行：

```bash
cd jewelry-qms
php think qms:check-manual-procedure-alignment \
  --spec=docs/qms_manual_procedure_alignment_pilot-v0.1.json \
  --procedure-dir=../knowledge/internal/procedures \
  --output-dir=runtime/manual-procedure-alignment-v0.2 \
  --report-version=v0.2
```

不提供 `--trace-snapshot` 时，命令只读查询当前系统追溯关系；测试或离线复核可显式提供固定追溯快照。输出目录或同名报告已经存在时，命令会拒绝覆盖，必须提高报告版本或换新目录。

成功执行会打印五类结论数、追溯缺口数、阻断项数及三份报告路径。发现冲突属于正常业务结果，命令仍可返回 0；输入缺失、版本不唯一或规则执行失败会进入 `blockers` 并返回非 0。

## 四、如何读结果

| 状态 | 含义 | 处置 |
|---|---|---|
| `consistent` | 程序与要求一致 | 保留证据，抽查确认 |
| `conflict` | 明文矛盾或确定性规则冲突 | 登记修订意见，受控流程另行修改 |
| `missing` | 未找到要求承接 | 人工确认后决定补录或判不适用 |
| `review_required` | 岗位别名、语义或适用性不足以自动定案 | 必须由用户确认，不得按通过处理 |
| `not_applicable` | 已有明确不适用前提和证据 | 保存能力范围等支撑材料 |

`trace_source` 的优先级为正式块链接、要素映射、试点清单兜底。兜底扫描会登记为追溯缺口，不能把“扫到了文件”误当作系统追溯已经闭合。

## 五、建议工作流

1. 先依据有效标准修订手册草案，不直接改生成导出层。
2. 把本次变化拆成活动、期限、责任、记录、禁止/允许等原子要求，登记到版本化清单。
3. 运行只读校验，让现有追溯关系定位受影响程序并生成修订意见。
4. 用户确认 `review_required`、岗位别名和适用性后，再形成受控修订包。
5. 手册与受影响程序同批审批、发布；发布后重新导出并复跑校验。

当前试点证明“沿追溯链抓出程序硬冲突”可行，但尚未证明可以不经要求原子化就自动审完整套程序。扩大到全手册前，应逐类增加规则和反例测试，并继续保留人工复核闸门。

## 六、岗位责任链的后续设置

建议把岗位与职责单独建成“活动级责任链”，作为手册和程序共同引用的结构化控制对象，而不是继续分散在各文件自由书写。最小字段应包括：活动、编制/执行、复核、批准、监督、岗位标准名、受控别名、适用场所、依据条款和承接文件。

第二阶段可先做数据盘点和页面设计；在用户确认岗位标准名与别名之前，不自动建表、不自动改文、不把候选关系定案。
