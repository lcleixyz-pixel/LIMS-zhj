# G4-R9 异常入口根因与影响评估 v0.1

生成时间：2026-07-15
阶段：规划，不执行治理。

## 1. 结论先行

G4-R8 的 39 个业务异常入口不是全站性故障，分为两类：

1. 38 个来自 `/planning/structures/package` 组合包页面。根因是页面读取 2026-07-11 的历史组合包 manifest，其中保存了旧的 `block_id`，但这些内容块已不在当前 `qms_document_blocks` 表中。页面仍把这些历史 `block_id` 显示成“编辑内容块 / 复核追溯”现行操作按钮，用户点击后进入错误页。
2. 1 个来自 `/calendar/index` 本月待办。根因是 `notifications` 表中有一条提醒指向不存在的设备维护记录 `00000000-0000-0000-0000-00000000b002`。

最重要的治理原则：不要把历史归档当成当前业务对象删除。组合包归档应保留为证据，只是不能继续提供“编辑当前对象”的入口。

## 2. 已查证据

### 2.1 组合包异常

异常入口示例：

- `/planning/structures/blocks/edit?id=ae45ee91-c6ab-409c-b5fd-71e8bf0dc3f1`
- `/planning/structures/links/review?block_id=ae45ee91-c6ab-409c-b5fd-71e8bf0dc3f1`

来源页面：

- `/planning/structures/package`

代码路径：

- `PlanningStructure::package()` 给页面传入 `latestSystemPackageBlockTraceRows()`
- `latestSystemPackageBlockTraceRows()` 读取 `runtime/qms_structured/system_package/archive/manifest.json`
- `normalizePackageBlockTraceRows()` 对 manifest 行拼出：
  - `block_edit_url`
  - `trace_review_url`
- `package.html` 直接渲染“编辑内容块 / 复核追溯”按钮

数据库核查：

- 这些坏 `block_id` 在当前 `qms_document_blocks` 中不存在。
- 这些坏 `block_id` 在当前 `qms_document_block_links` 中不存在。
- 这些坏 `block_id` 在当前 `qms_document_change_logs.block_id` 中不存在。
- 这些坏 `block_id` 来自 `manifest.json` 的 `block_trace_inventory`。

归档信息：

- manifest 路径：`jewelry-qms/runtime/qms_structured/system_package/archive/manifest.json`
- 生成时间：`2026-07-11 19:20:06`
- package version：`1`
- block trace inventory：`1021`
- 旧块所属文件：`CNAS-CL01-A015:2018`
- 当前同文件仅剩 1 个 overview 块，旧条款块已不再是当前可编辑块。

### 2.2 日历待办异常

异常入口：

来源页面：

- `/calendar/index`

数据库核查：

`equipment_maintenances` 表中不存在该 ID。

`notifications` 表中存在一条活动提醒：

- title：设备相关到期提醒
- link_controller：`equipment_maintenance`
- link_action：`view`
- link_id：`00000000-0000-0000-0000-00000000b002`
- due_date：`2026-07-12`
- notification_key：`equipment_verification_due:00000000-0000-0000-0000-00000000b002:2026-07`
- publish：`1`
- soft_delete：`0`

## 3. 严格影响评估

| 风险点 | 如果误治会怎样 | 建议控制 |
|---|---|---|
| 删除组合包 manifest | 丢失历史体系文件组合包证据，影响溯源链审计 | 不删除，只在页面层标记历史快照 |
| 重写 manifest | 可能改变历史包 hash 和版本证据 | 不直接改旧 manifest；如需新包，生成新版本 |
| 批量删除 qms_document_blocks | 可能破坏当前结构化文件、表格模板追溯、法规影响链 | 禁止作为第一治理手段 |
| 直接软删所有异常通知 | 可能隐藏真实待办 | 只处理已确认目标不存在的单条通知，且先做只读清单 |
| 控制器全部吞掉 404 | 可能掩盖真实数据问题 | 只做用户友好降级，同时保留日志/提示 |
| 组合包页继续提供历史编辑按钮 | 用户会误以为历史对象可编辑，点击进入错误页 | 历史 manifest 行只显示“历史快照”，不显示编辑/复核按钮 |
| 重新生成组合包 | 会新增运行时归档文件，改变“最新包” | 放在单独闸门，先经用户批准 |

## 4. 治理策略

### 推荐路径：先页面保护，再数据清理

第一步不碰历史归档、不碰当前结构化数据，只修“坏入口暴露”。

核心规则：

- 如果 manifest 中的 `block_id` 在当前 `qms_document_blocks` 不存在，则该行仍可展示为历史追溯快照，但不显示“编辑内容块 / 复核追溯”按钮。
- 如果 `structured_document_id` 仍存在，可保留“查看文件”入口；如果也不存在，则显示“历史归档对象已失效”。
- 对控制器 `editBlock()` / `reviewLinks()` 补友好降级，避免用户直接访问旧 URL 时看到 ThinkPHP 错误页。
- 日历待办入口只在目标记录存在时显示“前往处理”；目标不存在时显示“对象已不存在，请复核提醒来源”。

### 不推荐路径

- 不建议直接删除 `manifest.json`。
- 不建议直接把旧 block_id 从 manifest 中抹掉。
- 不建议把 `qms_document_blocks` 重新造回旧 ID，因为这会制造“假现行数据”。

## 5. 分闸门计划

### G4-R9-A：只修页面与服务保护层

目标：不改数据库，不改历史归档，只让页面不再暴露坏入口，并让直接访问旧 URL 时不出现框架错误页。

拟修改文件：

- `jewelry-qms/app/service/QmsDocumentStructureService.php`
- `jewelry-qms/app/controller/PlanningStructure.php`
- `jewelry-qms/app/view/planning_structure/package.html`
- `jewelry-qms/app/controller/Calendar.php`
- `jewelry-qms/app/view/calendar/index.html`
- 新增测试：`jewelry-qms/tests/qms_g4r9_stale_link_guard_smoke.php`

影响：

- 只影响 UI 展示和错误降级。
- 不改变任何质量记录。
- 不改变历史组合包 hash。
- 不改变正式追溯关系。

验收标准：

- `/planning/structures/package` 不再渲染指向不存在 block_id 的“编辑内容块 / 复核追溯”按钮。
- 页面仍能展示历史追溯摘要。
- 直接访问旧 block URL 时，返回友好提示并引导回组合包或结构化文件列表。
- `/calendar/index` 对目标不存在的提醒不再显示坏链接。
- G4-R8 中 39 个业务异常入口重新跑，不能再出现 ThinkPHP 错误页。

### G4-R9-B：可选重新生成组合包

目标：在 A 步通过后，由用户批准后生成一个新的组合包版本，使最新 manifest 与当前内容块一致。

拟执行：

- 先备份当前 `manifest.json` 和现有组合包归档。
- 运行系统内“生成体系文件组合包”动作或等价命令。
- 比对新 manifest 中 `block_trace_inventory` 的 block_id 是否全部存在于当前表。

影响：

- 会新增 runtime 归档文件。
- 最新组合包版本会改变。
- 不应删除旧归档。

验收标准：

- 最新组合包的所有 `block_edit_url` / `trace_review_url` 均可打开或被正确降级。
- 历史版本仍可追溯。

### G4-R9-C：单条通知残留治理

目标：处理 `notifications` 中指向不存在设备维护记录的单条提醒。

治理选项：

1. 页面层保护：目标不存在时不显示“前往处理”，保留提醒但提示“关联记录不存在”。
2. 数据层关闭：经用户批准后，将该单条通知 `soft_delete=1` 或 `publish=0`。

推荐：先做页面层保护；若后续确认是验收残留，再批准单条关闭。

影响：

- 页面层保护不改变数据。
- 单条关闭会改变待办显示，但不影响设备维护记录，因为目标记录本来不存在。

## 6. 回退方式

G4-R9-A：

- 代码改动可通过 Git diff / commit 回退。
- 因不写数据库、不改 runtime 归档，回退风险低。

G4-R9-B：

- 生成新组合包前复制当前 `manifest.json` 和 archive 文件清单。
- 如新包异常，可恢复旧 manifest；但历史新归档文件可保留，不必删除。

G4-R9-C：

- 若只做页面保护，回退代码即可。
- 若关闭单条通知，需记录原始字段；可将 `publish` 或 `soft_delete` 恢复。

## 7. 建议批准口径

建议先批准：

> 批准 G4-R9-A：只修页面与服务保护层，不写数据库，不改历史组合包归档，不部署云端。

暂不建议一次性批准：

- 重新生成组合包。
- 数据库清理。
- 云端部署。
