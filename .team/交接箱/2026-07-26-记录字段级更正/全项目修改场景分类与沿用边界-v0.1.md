# 全项目修改场景分类与沿用边界 v0.1

日期：2026-07-26  
适用范围：8021 治理试运行沙箱  
性质：只读盘点和后续设计依据，不代表已经实施

## 一、目的和边界

本文件用于判断 `jewelry-qms` 中不同对象发生修改时，应采用直接编辑、批注更正、修订换版还是追加事件，避免把本轮记录批注能力机械复制到所有模块。

本轮只核对现有控制器、状态、审计日志和已形成的记录更正链，不修改页面、代码、数据库或现有业务数据。

## 二、采用的统一判断规则

| 代码 | 修改方式 | 适用条件 | 核心要求 |
|---|---|---|---|
| M1 | 草稿直接编辑 | 尚未批准、发布、完成或被其他业务引用 | 保存即可；重要字段保留字段变更日志 |
| M2 | 批注更正 | 已形成记录证据后发现事实填错、漏填 | 原值冻结；申请、审批后只追加更正；当前视图展示最终状态；原始版本可追溯 |
| M3 | 修订换版 | 制度、方法、模板、职责规则或受控内容发生变化 | 旧版冻结；建立新草稿版本；影响分析、冲突审查、重新签批和生效 |
| M4 | 追加事件 | 对象本身没有填错，只是后续状态发生变化 | 新增校准、维护、转移、评价、关闭、撤销等事件，不覆盖历史事实 |
| M5 | 作废标注 | 原记录不应继续使用，但必须保留证据 | 标明作废原因、人员和时间；禁止物理删除已形成的受控证据 |

判断口诀：

- 尚未形成证据：可以改。
- 已形成证据但填错：批注更正。
- 管理要求发生变化：修订换版。
- 业务状态继续发展：追加事件。
- 原内容不能再使用：作废标注，不直接删除。

## 三、条款和内部文件依据

- ISO/IEC 17025:2017 7.5.2：技术记录变更应可追溯，原始数据和修订数据均应保留，并记录变更日期、内容和责任人员。
- ISO/IEC 17025:2017 7.8.8：已发布报告的修订应明确标识修订原因和内容，并引用原报告。
- ISO/IEC 17025:2017 7.11.2—7.11.3：信息系统及其变更应授权、留痕、验证，并保护数据完整性。
- ISO/IEC 17025:2017 8.3：受控文件应识别版本和变更，防止误用失效版本。
- ISO/IEC 17025:2017 8.4：记录应保持清晰、可检索、受保护并按要求留存。
- 内部衔接对象：`XZTC/CX-08-2022`《文件控制程序》、`XZTC/CX-19-2022`《记录控制程序》、`XZTC/CX-26-2022`《计算机文件及数据控制程序》、`XZTC/CX-29-2022`《结果报告管理程序》。

以上内部程序仅作为现有体系衔接对象；本轮没有认定其具体条文已经充分覆盖电子更正要求。

## 四、全项目修改场景分类

| 对象或模块 | 草稿/形成证据前 | 批准、发布、完成或形成证据后 | 推荐主方式 | 当前基础和主要缺口 | 优先级 |
|---|---|---|---|---|---|
| 体系文件 `Document` | M1 | M3；失效时 M5 | 修订换版 | 已限制非草稿编辑，并能建立新修订草稿、保留旧版和重新签批；继续沿用，不改成字段批注 | 已具备 |
| 记录表格模板 `RecordFormTemplate` | M1 | M3；失效时 M5 | 修订换版 | 已限制试运行就绪、已发布和已作废模板直接编辑；仍应补齐统一的新版本入口和版本差异展示 | P1 |
| 结构化手册/程序块 `PlanningStructure` | M1 | M3 | 修订换版 | 已有变更影响预览、修订说明和变更申请；应继续作为体系内容的来源治理链 | 已具备基础 |
| 外部依据、法规候选和变更事件 | 候选信息可补充 | M3+M4 | 新依据版本加变更事件 | 已有候选复核、变更事件和状态流转；不应覆盖旧依据内容 | 已具备基础 |
| 职责链、岗位任命和授权规则 | 草稿可编辑 | M3+M4；撤销用 M5 | 新职责版本、任命/撤销事件 | 已有职责链版本、审批和撤销状态；不适合做字段批注 | 已具备基础 |
| 记录实例 `RecordFormInstance` | M1 | M2；必要时 M5 | 字段/单元格批注更正 | 已实现原值冻结、结构化申请、审批、批注投影、当前状态 PDF 和原始 PDF 保留 | 已实施试点 |
| 培训活动及培训记录 | 计划或未完成记录可编辑 | M2；培训状态变化用 M4 | 完成后批注更正 | 培训可标记完成，但多数编辑仍继承通用逻辑；缺少完成后统一冻结 | P0 |

| 设备基础档案 `Equipment` | 建档和投用前 M1 | 事实填错用 M2；位置、状态变化用 M4 | 主数据加设备事件 | 已有校准、维护和转移子记录；应禁止用编辑设备主档替代转移、停用、维修等事件 | P1 |
| 校准、维护、期间核查 | 记录未完成前 M1 | M2；后续活动用 M4 | 完成后批注更正 | 现有记录可查看，部分业务会联动设备状态；缺少完成冻结和更正审批 | P0 |
| 标准物质/参考物质 | 建档或验收前 M1 | 事实填错用 M2；领用、核查、耗尽、过期、报废用 M4/M5 | 主数据加履历事件 | 已有状态字段，但应避免通过直接编辑抹去批号、有效期和状态履历 | P1 |
| 人员档案 | 联系信息等非证据字段可 M1 | 资格证书、任命、授权变化用 M4；事实填错用 M2 | 主档加资格/任命事件 | 已有证书、任命和职责链数据；应停用/撤销而非覆盖或删除历史授权 | P1 |

| 不符合工作 | 初始登记未提交前 M1 | 影响评价、处置、恢复和 CAPA 关联用 M4；关闭后错误用 M2 | 过程事件加关闭冻结 | 已有部分字段审计和 CAPA 创建入口，但缺少统一生命周期冻结 | P2 |
| CAPA | 初始草稿 M1 | 原因分析、措施、验证、有效性评价用 M4；关闭后错误用 M2 | 阶段事件加关闭冻结 | 已有状态推进、有效性评价和字段审计；应避免直接覆盖每一阶段已经确认的结论 | P2 |
| 内审计划、日程和检查表 | 计划草稿 M1 | 批准后调整用补充/变更事件 M4；完成后错误用 M2 | 批准后追加，完成后冻结 | 审核计划已限制非草稿编辑/删除；日程、检查表和发现项的控制不完全一致 | P1 |
| 内审发现及证据 | 初始登记 M1 | 责任、期限、处置、证据和关闭用 M4；关闭后错误用 M2 | 过程事件加关闭冻结 | 已有字段审计、证据附件和 CAPA 关联；仍需形成不可覆盖的处理链 | P1 |
| 管理评审及改进行动 | 会议草稿 M1 | 评审完成后 M2；行动状态和验证结果用 M4 | 完成后冻结、行动追加 | 已有完成和行动验证入口；缺少完成后统一更正路径 | P1 |
| 场所、部门、分类等基础配置 | 被引用前 M1 | 名称纠错可受控编辑；组织变化用 M4；停用用 M5 | 受控主数据 | 通用 CRUD 支持编辑和软删除；被历史记录引用后不应物理删除或改变历史显示含义 | P3 |
| 用户、密码、权限和系统配置 | 经授权直接变更 | M4 | 安全/配置变更日志 | 不属于业务记录批注；应记录操作者、时间、授权、变更内容和必要的验证结果 | P2 |
| AI、导入、接口和电子签批配置 | 测试配置可调整 | M4；正式配置变化需验证 | 授权变更加验证记录 | 应按 7.11.2 做配置变更确认，不能只记录最终配置值 | P2 |
| 检测报告（后续如纳入系统） | 出具前按报告流程修改 | M3/M5，不采用普通记录批注替代 | 修订报告或补充文件 | 新报告应有唯一标识并引用原报告；这是 7.8.8 的专门路径 | 建设时强制 |

## 五、现状判断

项目不是“完全没有修改治理”，而是已经形成三块可复用基础：

1. `Document` 已有草稿编辑、修订换版、签批、发布和作废链。
2. `PlanningStructure` 已有内容块修改、影响预览和修订申请。
3. `RecordFormInstance` 已有原记录冻结、字段级更正审批和最终状态输出。

当前共性缺口是：

1. 多数业务模块继承 `CrudBase::edit()`，保存时直接覆盖原字段。
2. `CrudBase::delete()` 对带 `soft_delete` 的对象可直接软删除，但尚未统一判断对象是否已形成受控证据或被其他对象引用。
3. 字段审计目前只覆盖部分模型；它能说明“谁把什么值改成什么”，但不能替代更正申请、审批、原始值冻结和当前状态输出。
4. `field_values` 等 JSON 字段在通用审计日志中仅显示“已变更”，不足以证明具体改动内容；记录实例已用专门更正链弥补。
5. 不同模块的“完成、关闭、批准、发布”状态尚未统一接入生命周期写入闸门。

## 六、推荐的最小沿用方式

不先建设一个庞大的通用工作流平台。后续每个试点只复用五项最小能力：

1. 明确何时从“可编辑”变成“已冻结”。
2. 冻结后移除直接编辑和删除入口。
3. 事实填错时，复用“选择字段—读取原值—申请—审批—追加更正”。
4. 状态变化时新增事件，不伪装成字段更正。
5. 详情页展示当前状态，同时保留原始记录和完整修订链。

## 七、建议试点顺序

### 第一试点：培训记录

原因：字段结构直观，完成状态明确，风险低，适合验证“完成前可编辑、完成后批注更正”。

最小范围：`Training`、`TrainingRecord`；暂不同时改造人员任命和能力授权。

### 第二试点：校准记录

原因：记录完整性直接影响设备状态和计量溯源，能够验证“记录更正”和“后续业务事件”不能混为一谈。

最小范围：`Calibration`；维护、期间核查和设备转移在校准试点稳定后再沿用。

### 暂不作为首批

- 文件、模板和结构化体系内容：现有换版链优先，不需要再套记录批注。
- 投诉、不符合和 CAPA：跨阶段、跨岗位、跨证据关联较多，应在简单记录试点稳定后治理。
- 人员、设备、供应商主档：需要先区分“事实纠错”和“业务状态事件”，不宜直接复制记录实例界面。

## 八、后续实施闸门

本文件只完成分类。进入任何模块实施前，应再确认该模块：

1. 哪个状态开始冻结。
2. 哪些字段允许事实更正。
3. 哪些变化必须新增事件。
4. 谁申请、谁审批。
5. 当前状态输出是什么，原始版本从哪里下载。
6. 是否影响其他对象、统计、PDF、签批或外部报告。

未经模块级设计确认，不批量改造全部控制器。
