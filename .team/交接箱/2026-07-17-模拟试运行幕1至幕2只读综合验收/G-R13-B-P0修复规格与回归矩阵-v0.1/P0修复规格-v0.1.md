# P0 修复规格

> 版本：v0.1  
> 日期：2026-07-17  
> 基线：分支 `codex/g4-r12-cloud-deploy-prep`，commit `04c29249769c09ce2d4b9bad3e690592f25249c2`  
> 来源：G-R13-A 的 RC-01～RC-04  
> 状态：内部实施候选；不代表已修复、已迁移或已部署。

## 1. 目标与红线

目标是消除四类会破坏质量记录可信度的 P0 根因：

1. 新增、列表、详情、编辑与数据库字段不一致；
2. 写入结果、UUID、编号、跳转和来源关联不一致；
3. 页面角色过粗、缺少动作级和场所级授权；
4. 关键记录的变更历史缺失、失真或对岗位人员不可读。

红线：

- 不重建收样、检测、报告业务模块；外部检测业务只通过稳定标识和只读链接接入。
- 不自动修复无法唯一判断来源的数据；先快照、扫描、形成候选修复清单，再人工确认。
- 不增加“设备管理员、资料员、内审员”等新的粗粒度登录角色；复用已批准的 `employee_appointments + qms_positions + site_id`。
- 不把系统管理员身份当作业务批准身份；系统管理员可维护系统，但业务动作仍应记录实际岗位依据。
- 不绕过记录模板、文件批准和法规候选的人工确认门禁。

## 2.1 质量管理依据

| 关注点 | ISO/IEC 17025:2017 / CNAS-CL01 对应条款 | 本规格落实方式 |
|---|---|---|
| 职责、权限和相互关系 | 5.5、6.2.4～6.2.6 | 业务岗位任命与动作、场所范围关联，不以管理员身份替代业务授权 |
| 技术记录修改可追溯 | 7.5.2 | 保存原值、新值、操作者和时间；无变化不生成假记录 |
| 投诉处理 | 7.9 | 投诉登记、调查、处置、CAPA 和关闭权限分离且可追溯 |
| 不符合工作 | 7.10 | 不符合的识别、影响评价、决定、责任和 CAPA 链保持一致 |
| 数据和信息管理 | 7.11.2、7.11.3 | 投用前验证、访问控制、数据完整性、失败回滚和审计追踪 |
| 记录控制 | 8.4 | 软删除不可继续作为有效记录访问，历史变更证据可检索 |

这些条款要求的是结果可控、权限适当和记录可追溯；本规格中的具体页面、服务和测试设计是实现方式，不把某一种技术结构误写成标准唯一强制方案。

## 3. RC-01：字段契约统一

### 3.1 唯一字段契约

| 模块 | 列表最小字段 | 新增/编辑允许字段 | 详情必须显示 | 不得由通用编辑修改 |
|---|---|---|---|---|
| 能力确认 | 员工、检测项目、评价日期、结果、有效期 | `employee_id,test_item,method_standard,assessment_date,assessor_id,result,authorization_scope,valid_until` | 前述全部字段及创建/修改时间 | `id,company_id,publish,soft_delete` |
| 不符合工作 | 编号、发现日期、来源、严重度、状态、责任人 | `nc_number,identified_date,source,severity,disposition,report_number,assigned_to,description,impact_assessment,immediate_action` | 前述字段、CAPA 链接、变更历史 | `status,capa_id,created_by`；状态另走明确工作流 |
| CAPA | 编号、来源、描述、责任人、期限、状态 | 编辑仅允许 `assigned_to,due_date,description,root_cause,corrective_action,preventive_action,verification` | 来源业务编号及链接、全部措施、验证、变更历史 | `capa_number,source_type,source_record_id,source_id,status` |
| 客户投诉 | 投诉编号、受理日期、客户、责任人、期限、状态 | `complaint_number,customer_name,contact,received_date,report_number,assigned_to,due_date,description` | 前述字段、调查/处理/反馈、CAPA 链接、变更历史 | `status,capa_id,investigation,handling,response,closed_date`；处置内容走 `advance` |

### 3.2 服务端要求

- 每个控制器声明自己的验证规则；不得再依赖模板里的 HTML `required` 作为唯一校验。
- 编辑请求只提取白名单字段，未知字段一律忽略并写安全日志；禁止 `$record->save($request->post())` 全量透传。
- 列表显示业务编号和姓名，不显示 UUID 作为主标签。
- `view/edit/delete` 必须追加 `soft_delete=0`；软删除记录返回 404，不得通过旧 URL 继续读取。
- 校验失败返回原表单、保留安全字段值，不产生写入，也不显示 SQL、路径、会话或调用栈。

### 3.3 验收条件

- 四模块全部完成“新增→列表→详情→编辑→详情”闭环。
- 编辑未提交的字段保持原值；不符合、投诉状态不被通用编辑改变。
- 缺必填字段时数据库行数不变，用户看到中文字段级提示。

## 4. RC-02：编号、UUID、事务和双向关联

### 4.1 编号生成

- 只把当年固定前缀之后的部分解析为流水号：`CP` + `2026` + `001`。
- 已存在异常编号不得参与当年最大序号计算；记录到预检报告，由人工决定是否更正。
- `complaint_number`、`capa_number`、`nc_number` 在公司范围内必须唯一；迁移加唯一索引前先做重复扫描，扫描不为零则阻断迁移。
- 本轮只修已证实的后缀解析错误；并发序号服务如没有可重复失败证据，不在 P0 中扩建新子系统。

### 4.2 CAPA 来源关联

`WorkflowService::createCapaFromSource()` 必须满足：

1. 来源类型只允许 `audit/complaint/nc/review/internal`；有来源记录时先确认记录存在且未软删除。
2. 传入和返回 ID 均为非空字符串；数据库主键以 36 位 UUID 保存，不使用 `lastInsertId()`。
3. “创建 CAPA + 回写来源 `capa_id`”处于同一事务；任一步失败整体回滚。
4. 对 `(source_type, source_record_id)` 幂等：已有关联时返回既有 CAPA，不再新建第二条。
5. 创建成功后跳转到真实 `$capa->id`；来源详情与 CAPA 详情可相互打开并显示业务编号。
6. 通知在事务提交成功后发送；通知失败不得伪装成业务写入失败，但应留下运维日志。

### 4.3 数据处置边界

- 新增只读命令 `qms:p0-preflight`，输出重复编号、无效 UUID、孤儿 CAPA、来源反向不一致、软删除记录可访问性等统计和候选行 ID。
- 预检不得更新任何记录。
- 修复脚本必须读取“人工确认映射表”，没有唯一映射的行保持阻断；禁止按数字 `1/2` 猜测目标 UUID。
- 本机、云端分别生成快照和预检报告，不以本机为云端结论。

## 5. RC-03：动作级和场所级授权

### 5.1 架构决定

保留现有 5 个登录角色作为“页面入口粗筛”，新增 `ActionAuthorizationService` 作为“具体动作复核”。业务岗位来自现行且已批准的任命：

`users.employee_id → employee_appointments → qms_positions.code`，同时校验任命有效期、状态、`publish/soft_delete` 和 `site_id`。

页面按钮使用 `qms_can_action(module, action, record)` 控制可见性；服务端必须再次调用同一策略，不能只隐藏按钮。

### 5.2 候选动作矩阵

本矩阵根据已确认组织口径形成，进入代码前仍需质量负责人签字确认；姓名仅用于验收人员映射，代码不得写死姓名。

| 模块/动作 | 允许岗位 | 场所规则 | 备注 |
|---|---|---|---|
| 投诉登记、查看本人经办记录 | 一般人员、资料管理员、质量负责人、场所质量协调人 | 本场所或本人登记 | 保留员工主动登记入口 |
| 投诉调查、推进、创建 CAPA、关闭 | 质量负责人、场所质量协调人 | 质量负责人全机构；协调人按任命范围 | 一般人员不得执行 |
| 不符合登记 | 技术负责人、质量负责人、场所质量协调人、部门负责人 | 按记录场所 | 允许发现者提交“报告”，正式处置另行授权 |
| 不符合处置、触发 CAPA、关闭 | 质量负责人；技术处置可由技术负责人执行 | 按场所任命 | 关闭与验证不得由同一未经授权人员自批 |
| CAPA 编辑措施 | 质量负责人、被指派责任人 | 被指派人仅限自己负责记录 | 被指派人不得自行验证关闭 |
| CAPA 验证/关闭 | 质量负责人或被明确任命的验证人 | 全机构或任命范围 | 必须记录业务岗位 |
| 能力确认新增/编辑 | 技术负责人、质量负责人 | 按人员所属场所 | 评价人与被评价人不得混淆 |
| 设备记录只读审核 | 内审员 | 被派审核范围；不得审核本人工作 | 解决 auditor 完全看不到设备证据的问题 |
| 设备维护写入 | 设备管理员、技术负责人 | 严格按任命场所 | 内审员只读 |
| 模板复核清单只读 | 资料管理员、质量负责人、内审员 | 机构范围 | “看清单”不是编辑动作 |
| 模板草拟/字段修订 | 资料管理员、质量负责人 | 资料管理员按文件职责 | 发布批准仍由授权岗位完成 |
| 模板批准发布 | 质量负责人或体系规定的批准岗位 | 机构范围 | 系统管理员身份不自动获得业务批准权 |

组织验收映射：质量负责人张晓磊；场所质量协调人刘恒春；乌鲁木齐技术负责人曹红；和田技术负责人李成辉；内审组按实际派组记录；资料管理员和设备管理员按两个场所现行任命验证。CMA 登记最高管理者仍为俞炳星，不因系统中存在其他管理身份而改写备案事实。

### 5.3 拒绝响应

- 未登录：401 或跳转登录。
- 已登录但无权限的页面 GET：403 友好页，说明“无此动作权限”和联系岗位，不泄露权限配置细节。
- 越权 POST/AJAX：HTTP 403；数据库、审计业务表均不改变，但安全审计记录一次失败尝试。
- 菜单可见不等于动作可写；拒绝响应不得经过工作台重定向后变成 HTTP 200。

## 6. RC-04：关键记录留痕

### 6.1 覆盖范围

在现有 Document、CAPA、Equipment、AuditFinding、外部变更事件基础上，增加：

- `Nonconformity`：来源、严重度、描述、影响评估、即时措施、处置、责任人、状态、CAPA；
- `CustomerComplaint`：客户、报告编号、描述、调查、处理、反馈、责任人、期限、状态、CAPA、关闭日期；
- `CompetencyRecord`：员工、项目、标准、评价日期、评价人、结果、授权范围、有效期；
- `QmsExternalChangeCandidate`：人工确认状态、确认人、时间、备注、关联正式事件；
- `Equipment`：继续覆盖状态、下次/上次校准日期、场所，但修复无实际变化却写日志的问题。

### 6.2 留痕规则

- 比较前统一规范 `null/''`、日期字符串、布尔/整数和枚举；语义相同不得生成日志。
- 长文本可截断展示，但必须保存可辨识的前后值摘要；日期不得显示 `[已变更]`。
- 详情页显示中文字段名、业务可读值、操作人姓名/岗位、时间；不得只显示 UUID。
- 关键模型的业务写入和字段审计处于同一事务。审计表不可用或写入失败时，关键业务写入回滚并显示“系统未能保存完整变更记录，请联系管理员”。
- 失败授权尝试进入安全审计，不进入业务字段变更历史。

### 6.3 验收条件

- 每次真实字段变更恰好产生对应日志；无变化保存产生 0 条。
- 修改两个字段只出现两条，不出现未触碰字段。
- 不符合、投诉、能力确认和法规候选详情均可看到历史。
- 操作人、时间、字段、原值、新值完整；关键写入不能在审计失败时单独成功。
