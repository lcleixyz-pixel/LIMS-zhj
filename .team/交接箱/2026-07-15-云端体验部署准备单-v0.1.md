## 2. 必须保留的边界

- 本环境只用于人员体验、熟悉系统、模拟测试和流程试运行。
- 不录入正式检测业务数据、客户资料、身份证明、受控体系原件或其他敏感信息。
- 数据库不开放公网端口；应用只绑定 `127.0.0.1:18010`，公网入口由宝塔 Nginx 反向代理。
- 宝塔入口必须先有 HTTPS 和独立 BasicAuth，再开放给员工体验。
- 服务器不从 Docker Hub 拉取关键镜像、不在服务器构建镜像；使用本机验证过的 `linux/amd64` 镜像包上传。
- 密码只在服务器生成，不进 Git、不进聊天、不进交接文档。

## 3. 建议分闸门

### G0：代码收口与发布基线冻结

目标：确定本次部署使用哪个代码基线。

建议：先保留 PR #31 为 Draft，不合并 main；以 PR #31 当前内容作为体验部署 release candidate。若体验测试通过，再决定是否合并 main。

验收：

- PR #31 可打开、分支存在、工作区干净。
- 打包前用 `git rev-parse --short HEAD` 固定 release id，例如 `regmon-20260715-<short-sha>`。

### G1：服务器只读体检

目标：只看服务器状态，不安装、不启动、不改配置。

检查：

- 主机、系统、磁盘、内存、CPU、Docker/Compose 是否可用。
- 端口 `18010` 是否被占用。
- 宝塔现有网站 `zhj-jc.com` 与测试域名 `qms.zhj-jc.com` 状态。
- `/www/server/` 下是否已有同名目录或历史部署痕迹。
- 防火墙、Nginx、证书、BasicAuth 支持情况。

验收：

- 出一份 G1 只读体检记录。
- 明确是否可进入 G2。

### G2：本机 release 包与 amd64 镜像包

目标：在本机生成服务器可接收的代码包、镜像包和校验文件。

动作：

- 从 PR #31 当前 HEAD 导出 release 代码包。
- 本机完成 `linux/amd64` 镜像构建或导出。
- 生成 `SHA256SUMS`。
- 本机验证镜像架构为 `amd64/linux`。
- 本机验证 `deploy/experience/compose.yaml` 的关键安全项：`APP_DEBUG=false`、MySQL 无公网端口、应用仅回环绑定、数据库使用内部网络。

验收：

- 形成本机打包验收记录。
- 服务器侧尚不启动应用。

### G3：上传与服务器解包

目标：只把已验证 release 放到服务器目录结构中。

动作：

- 创建 `/www/server/jewelry-qms-experience/releases/<release-id>`、`shared/`、`snapshots/`。
- 上传代码包、镜像包和校验文件。
- 校验 SHA-256。
- 在服务器生成 `.env`、数据库密码和 BasicAuth 密码。

验收：

- 目录结构正确。
- `.env` 权限为 600。
- 密码未写入 Git 或聊天。

### G4：启动体验环境与入口验证

目标：让 `qms.zhj-jc.com` 可受控访问。

动作：

- `docker load` 已验证镜像。
- `docker compose up -d --pull never`。
- 运行 `deploy/experience/verify.sh`。
- 宝塔配置 HTTPS、BasicAuth、反向代理到 `127.0.0.1:18010`。
- 验证公网未授权返回 401，授权后登录页可见。

验收：

- 应用 HTTP 回环返回 200。
- 数据库 healthy。
- DB 无宿主机端口。
- BasicAuth 生效。
- 形成 G4 上线体验记录。

### G5：试运行数据与回退演练

目标：让员工能体验，同时不把体验环境误当生产。

动作：

- 只导入脱敏或模拟数据。
- 做一次数据库快照。
- 做一次独立临时容器恢复演练，不覆盖当前数据卷。
- 记录初始账号、岗位体验范围和禁止录入提示。

验收：

- 快照可校验。
- 恢复演练可读表数量。
- 员工体验清单明确。
