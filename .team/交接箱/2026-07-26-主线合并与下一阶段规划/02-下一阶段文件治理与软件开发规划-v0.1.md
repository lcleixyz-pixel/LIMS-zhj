# 下一阶段文件治理与软件开发规划 v0.1

日期：2026-07-26

## 总目标

把“治理后的文件体系”尽快落在系统中试运行，形成可检查、可签批、可更正、可追溯的闭环；同时避免过重工程化，先把能直接改善试运行的东西做出来。

## 一、文件治理主线

### 1. 先做链条闭合，不先追求漂亮定稿

每份文件按同一条链检查：

外部依据 / 现用纸质文件 → 手册条款 → 程序文件 → 记录表格 → 系统运行证明。

验收标准：

- 外部依据能追到手册条款。
- 手册条款能追到程序文件落实方法。
- 程序文件能追到表格或系统记录。
- 表格字段足以证明程序过程确实运行过。
- 冲突和假设有明确标注，不把试运行材料当正式文件。

### 2. 优先治理文件

优先顺序建议：

1. `CX-03-02 标准物质管理程序`：已暴露真实链路问题，适合作为标准样板继续打磨。
2. `CX-19 记录控制程序`：关系到所有记录修改、更正、作废、留痕，是系统可信度地基。
3. `CX-08 文件控制程序`：关系到换版、签批、分发、受控打印。
4. `CX-26 计算机文件及数据控制程序`：关系到电子记录、PDF、DocuSeal、回调、备份。
5. `CX-01 / CX-01-02 人员培训与人员管理`：人员、岗位、授权、能力记录是试运行角色链的核心。
6. `CX-03 仪器设备管理程序`：设备、期间核查、维护、停用报废记录链条复杂，适合作为第二批深水区。

### 3. 每份文件的最小成品包

每份文件只要求形成 5 件轻量材料：

- 连续可读正文。
- 修订对照。
- 冲突审查。
- 程序—记录支撑清单。
- 8021 试运行装配结果。

## 二、软件开发主线

### 1. 建一个“文件治理工作台”

目标：让用户不用翻散文件，就能在一个页面看清某份文件的治理链。

最小功能：

- 左侧：现用文件 / 连续正文 / 修订对照 / 冲突审查。
- 右侧：对应手册条款、程序文件、记录表格、试运行状态。
- 顶部：当前阻断项、下一步动作、能否提交签批。
- 按钮：生成试运行稿、提交签批、复制为新版本、查看记录支撑。

### 2. 把“批注式修改”抽成通用能力

已经在记录更正里验证过：冻结原记录，只往上增，不往下减；修改人、修改时间、原因、字段目标、前后值都保留。

下一步沿用到：

- 体系文件修订。
- 记录模板换版。
- 人员能力记录。
- 设备档案。
- 供应商/外部服务记录。

### 3. 做一个“试运行验收面板”

目标：不靠口头问“跑通了吗”，而是页面直接告诉用户：

- 哪些文件已试运行就绪。
- 哪些还只是草稿。
- 哪些存在冲突。
- 哪些已走过签批。
- 哪些记录表格已经能证明程序运行。
- 哪些模块还有页面错误或无反馈。

### 4. 保留沙箱重置能力

8021 已经被用于真实模拟操作，状态会变化。后续需要一个轻量命令：

- 重置 8021 到治理试运行基线。
- 保留用户指定的验收样例。
- 输出重置前后差异。

这样测试不会被历史操作污染，也不会误伤 8010。

## 三、下一步执行建议

下一步我建议直接做：

> 文件治理工作台 v0.1：先以 CX-03-02 为样板，把“来源—正文—冲突—记录表—试运行状态—签批入口”放在一个页面。

理由：

- 它能同时推进文件治理和软件可用性。
- 它能减少用户在多个菜单间来回找入口。
- 它能把刚才发现的 BG-35-03 这类链条漂移直接暴露出来。
- 它不会要求马上搬正式运行记录，仍符合“先治理、再迁移、后内审”。
