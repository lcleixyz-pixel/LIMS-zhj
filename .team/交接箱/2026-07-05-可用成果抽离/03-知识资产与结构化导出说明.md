# 知识资产与结构化导出说明

## 1. 这部分是什么

`knowledge/internal/` 是当前项目已经能单独拿出来使用的知识资产导出层。它来自 `jewelry-qms` 的结构化库，而不是人工手写的一份孤立 Markdown。

它的价值在于：

- 把现用质量手册和程序文件变成可读、可搜索、可版本控制的 Markdown。
- 为后续 ISO 17025、CNAS、CMA 条款映射和专家智能体提供输入。
- 为人工抽检提供转换报告，明确哪些文件已导出、哪些仍需复核。

## 4. 导出链路

当前链路应按以下方式理解：

```text
现用文件/
  -> CurrentFilesSeedService 枚举和解析
  -> QmsDocumentStructureService 进入结构化库
  -> qms_structured_documents / qms_document_blocks
  -> exportKnowledgeInternal()
  -> knowledge/internal/
```

关键原则：

1. `knowledge/internal/` 是单向导出层。
2. 不应手工修改导出的 Markdown 当作正式源。
3. 如果发现解析问题，应修结构化库或解析服务，再重新导出。
4. 后续条款映射、块级追溯、记录表格 schema 都应回到系统数据模型中维护。

## 5. 可重跑命令

只枚举 2022 程序文件并导出清单：

```bash
cd /Users/lc.leixyz/Documents/AI工作台/01-项目代码/LIMS-zhj/jewelry-qms
php think qms:seed-current-files --enumerate-procedures
```

从已有结构化库导出 `knowledge/internal/`：

```bash
php think qms:seed-current-files --export-knowledge-internal
```

先刷新结构化库，再导出：

```bash
php think qms:seed-current-files --refresh-structures --export-knowledge-internal
```

谨慎边界：

- `--export-knowledge-internal` 会写 `knowledge/internal/` 里的导出文件。
- `--refresh-structures` 会刷新结构化库相关内容，应确认连接的是开发库或容器库。
- `--apply` 是正式写入现用文件初始化数据的选项，未经确认不要随手加。

## 6. 导出文件的字段意义

每份内部文件卡片通常包含 frontmatter，例如：

```yaml
doc_number: "XZTC/CX-26-2022"
type: "internal_procedure"
generated_from: "qms_structured_documents"
manual_edit: false
source_path: "现用文件/程序文件/程序文件2022/26-2022计算机文件及数据控制程序.docx"
```

这些字段说明：

| 字段 | 含义 |
|---|---|
| `doc_number` | 受控文件编号。 |
| `type` | 内部手册或内部程序文件。 |
| `generated_from` | 生成来源是结构化库。 |
| `manual_edit` | 当前导出文件不应手工维护。 |
| `source_path` | 原始现用文件位置，便于人工抽检。 |

## 7. 已可用于哪些工作

`knowledge/internal/` 当前已经可用于：

- 快速浏览现用质量手册和程序文件内容。
- 检查某个程序文件是否已被结构化导出。
- 给 QMS 文档起草、差距分析、合规评审提供内部语料。
- 作为后续 `knowledge/standards/` 条款卡片库的映射对象。
- 生成“条款 -> 文件 -> 记录 -> 运行证据”追溯矩阵的输入。

## 8. 还不能直接用于哪些工作

当前还不能直接宣称：

- ISO 17025 4-8 章标准卡片已全覆盖。
- CNAS / CMA 差异卡已全覆盖。
- 每份程序文件已完成条款映射。
- 结构化转换已通过人工逐段抽检。
- AI 问答引用这些卡片时一定无幻觉。

正确口径是：

> 内部体系文件结构化导出层已经可用，当前导出 1 份质量手册和 37 份程序文件，并保留 1 个明确待复核边界项。下一步应做人工抽检和条款映射。
