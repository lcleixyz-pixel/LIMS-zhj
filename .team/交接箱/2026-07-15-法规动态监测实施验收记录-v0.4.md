## 1. 本轮问题与治理结果

### 1.1 晋升故障分类

旧控制器捕获所有 `Throwable` 并返回 302，导致数据库、程序或依赖故障被伪装成业务拒绝。本轮通过正常构造器依赖注入增加可替换的 promotion callable，生产默认仍调用 `ExternalChangeEventService::promoteRegulatoryCandidate`，并完成以下分类：

- `RegulatoryPromotionDomainException`：作为业务拒绝，安全记录异常类名和候选 ID 哈希，返回候选详情和统一提示；
- 其他 `Throwable`：安全 `Log::error`，只记录异常类名和候选 ID 哈希，不记录原始消息或候选数据，随后原样重新抛出，由框架渲染 500。

### 1.2 成功审计归属

晋升成功审计不是由 AuditLog 中间件补写。`ExternalChangeEventService` 在创建事件、更新候选的同一业务事务内，原子写入唯一一条 `promoteRegulatoryCandidate` History；AuditLog 对该晋升请求不重复写通用 `promote` 审计。业务拒绝和系统故障均不写成功审计。

### 1.3 CSRF 证据范围

本轮 CSRF 证据包括：

1. 静态核对晋升 POST 路由位于包含 `FormTokenCheck` 的认证路由组；
2. 静态核对主布局 token meta、CSRF 助手和 POST 表单 `__token__` 注入接线；
3. `FormTokenCheck` 已记录的中间件语义：变更请求缺 token 时拒绝，有效 token 接受后消费，重放同一 token 时拒绝。

这些证据不等于完整 HTTP 路由调度或浏览器端到端测试，本记录不作扩大表述。

- Domain 业务拒绝仍返回 302 和统一安全提示；

### 3.7 False 探针：命令失败和缺少成功标记必须失败

使用与 3.1、3.3 相同的子 shell、`set -eu`、临时日志和 EXIT trap，将被测命令分别替换为“退出 23”和“成功退出但不打印 PASS”。来源门禁和 Compose 门禁实际结果一致：

```sh
set -eu
probe_gate() (
  set -eu
  label=$1
  mode=$2
  log=$(mktemp)
  trap 'rm -f "$log"' EXIT
  if [ "$mode" = command_failure ]; then
    if ! sh -c 'printf "%s\n" probe-command-failed; exit 23' >"$log" 2>&1; then
      cat "$log"
      exit 1
    fi
  else
    if ! sh -c 'printf "%s\n" probe-no-success-marker' >"$log" 2>&1; then
      cat "$log"
      exit 1
    fi
  fi
  cat "$log"
  tail -n 1 "$log" | grep -Eq '(passed|PASS)$'
)

probe_dir=$(mktemp -d)
trap 'rm -rf "$probe_dir"' EXIT
export TMPDIR=$probe_dir
for label in SOURCE_GATE COMPOSE_GATE; do
  for mode in command_failure missing_pass; do
    set +e
    output=$(probe_gate "$label" "$mode" 2>&1)
    code=$?
    set -e
    printf '%s_%s_EXIT=%s\n%s\n' "$label" "$mode" "$code" "$output"
    test "$code" -eq 1
    test "$(find "$probe_dir" -type f | wc -l | tr -d ' ')" -eq 0
    echo "${label}_${mode}_TEMPFILES=0"
  done
done
```

```text
SOURCE_GATE_command_failure_EXIT=1
probe-command-failed
SOURCE_GATE_command_failure_TEMPFILES=0
SOURCE_GATE_missing_pass_EXIT=1
probe-no-success-marker
SOURCE_GATE_missing_pass_TEMPFILES=0
COMPOSE_GATE_command_failure_EXIT=1
probe-command-failed
COMPOSE_GATE_command_failure_TEMPFILES=0
COMPOSE_GATE_missing_pass_EXIT=1
probe-no-success-marker
COMPOSE_GATE_missing_pass_TEMPFILES=0
```

上述结果证明：被测命令失败不会被后续 `cat`、`grep` 或清理覆盖；缺少成功标记返回 1；四次探针的临时文件均被清理。
