## 1. 审查问题与治理结果

v0.1 的服务层晋升和导出已通过，但岗位页面没有正式晋升入口，导出也没有详情按钮，无法支持完整岗位试运行。本次按回退方式继续，完成以下最小治理：

1. 新增 POST `/planning/regulatory-monitor/promote`，保持在 Auth、RBAC、PageContext、FormTokenCheck 和 AuditLog 路由组内。
2. 控制器只允许 `quality_manager`，操作人只取 Session，并只调用 `ExternalChangeEventService::promoteRegulatoryCandidate()`；控制器不直写数据库、不重复写成功 History。
3. 已确认相关候选向质量负责人显示带二次确认的晋升表单；已晋升候选显示关联事件入口。
4. 候选详情向管理员和质量负责人显示脱敏 JSON 导出按钮。
5. 端到端测试改为通过正式控制器晋升和导出，不再绕过岗位入口直接调用服务。
6. 新增晋升界面冒烟，覆盖角色/状态拒绝、跨机构、事务失败、Session 操作人、幂等和唯一成功审计。

## 3. 回归中发现并修复的测试门禁

首次批量回归于 2026-07-15 发现 `regulatory_impact_smoke.php` 报：

```text
A different analysis date must use a separate context snapshot
Expected: 2
Actual: 1
```

根因不是本次业务改动：测试默认时钟已到 2026-07-15，随后又把硬编码 2026-07-15 当作“不同日期”，实际命中同一缓存键。最小验证显示，默认时钟为 2026-07-14 时 context provider 调用 2 次，为 2026-07-15 时仅调用 1 次。测试现固定默认时钟为 2026-07-14，保留显式 2026-07-15 作为不同快照。

同时确认 ThinkPHP 控制台异常处理器只渲染未捕获异常，不自动设置非零退出码，旧脚本会出现“打印异常但 exit 0”。测试增加本地顶层异常处理器。临时故障探针实测：

```text
RuntimeException: temporary failure exit probe
PROBE_EXIT=1
employees=0
equipments=0
```

这证明未捕获失败返回 1，且数据库 fixture 的 `finally` 仍完成清理。探针随后撤销，正常脚本再次输出 `regulatory_impact_smoke passed`。

## 4. 全量验证与实际结果

### 4.1 双门禁规则

每个 PHP 冒烟脚本必须同时满足：

1. 进程退出码为 0；
2. 最后一行明确匹配 `passed` 或 `PASS`。

任一条件不满足即立即停止。Compose 脚本同样检查最终成功标记，防止框架异常处理造成假绿。

## 5. 数据与网络边界

- 端到端只使用仓库内“一单一库”离线夹具和随机测试标识。
- 业务数据库写入仅发生在 `lzhj-regulatory-test` 隔离库，并由 `finally` 清理。
- 来源安全测试真实断网；端到端测试不读取当日官网内容。
- 未使用本机真实业务数据、云端数据、生产密码或真实人员操作记录。

## 6. 仍保留的风险

| 级别 | 风险 | 当前控制/下一步 |
|---|---|---|
| 中 | 本次没有验证 2026-07-15 官方页面可达性和 HTML 结构 | 体验部署后先做单来源 DRY-RUN，再批准实际采集 |
| 中 | `manual_only` CMA 查询不能自动完成 | 指定人工查询、证据留存和复核责任 |
| 中 | 无运行时单来源自动停用开关 | 来源漂移时先关全局开关，用受控 `--source` 健康清单排查 |
| 低 | 两个不同候选同时晋升时，旧全局事件编号分配器可能令其中一个安全回滚 | 事务保证无半成品；核对后重试失败候选 |

备份/恢复演练、云端容器、HTTPS、真实数据迁移和定时任务实际启用仍属于后续部署闸门。
