# G4-R3 问题定位与修复记录 v0.1

## 结论

三个用户反馈均已处理：

1. 候选池不是用户没找到，而是此前没有页面和导航入口；
2. 变更事件新增页的 GET 报错来自 `stdClass` 与模板点号访问不兼容；
3. 首次 POST 复现的 500 是验证脚本未带 CSRF token，带 token 后登记保存流程通过；
4. 验证产生的 `G4R3-%` 事件和登录会话已清理。

## 根因与修复

| 问题 | 根因 | 修复 |
|---|---|---|
| 找不到候选池 | 代码已有候选表，但无控制器、页面、导航入口 | 新增只读 `PlanningRegulatoryCandidate` 控制器、模型、列表页和详情页；导航新增“法规候选池” |
| 变更事件新增页打开报错 | 新增页给模板传 `stdClass`，模板点号访问按数组处理 | `PlanningChangeEvent::add()` 改为传数组 |
| 变更事件保存验证时 500 | curl 验证未带 `__token__`，触发 `FormTokenCheck`；真实浏览器由 `csrf.js` 自动补 token | 验证脚本改为先从页面提取 CSRF token 再 POST；带 token 后保存成功 |
| `system_settings` 历史缺表隐患 | G4-R2 导入的基础 dump 未包含该运行配置表 | 将 `system_settings` 补入基础 schema，并在云端执行现有 migration 确保表存在 |
| 自动测试数据残留 | G4-R2/G4-R3 登录和验证流程产生会话/临时事件 | 清理 `user_sessions` 和 `G4R3-%` 验证事件；保留 intended 一单一库候选 |
