# 证据包归档策略 v0.1

日期：2026-07-26

## 目标

把治理试运行过程中产生的代码、交接记录、清单、样张和验收证据分层管理，避免仓库被 PDF/HTML 样张撑大，也避免试运行材料被误认为正式体系运行证据。

## 归档分层

### 1. 进入 Git 版本管理

适合长期追溯、体积可控、可 diff 的材料：

- 业务代码、服务、命令、测试脚本。
- Markdown 交接记录。
- JSON 清单、manifest、装配结果。
- SHA256 摘要文件。
- 与某次代码提交直接对应的最小复核说明。

### 2. 留在本地交接箱，不进入 Git

适合作为人工查看证据，但不适合长期塞进代码仓库的材料：

- PDF 样张。
- 大批量 HTML 样张。
- 生成型连续正文 HTML。
- Hermes 验收截图、PDF 证据目录。
- `jewelry-qms/.team/` 下的重复交接箱。

这些材料仍保留在本机 `.team/交接箱/` 中，需要外发或交叉复审时再单独打包。

### 3. 暂不裁决，后续单独处理

- `2026-07-25-8021治理体系试运行装配/GOV-TRIAL-0.2/`：含连续正文、冲突审查、装配清单、验证报告。它比本轮 G2/装配代码提交更接近“治理成品包”，建议后续单独做一次“正文包是否入仓 / 是否生成外发压缩包 / 是否只留本地”的裁决。
- `2026-07-26-记录字段级更正/`：Hermes 补充验收证据可作为本地复核材料，是否入仓需按体积和隐私再判断。

## 本次 `.gitignore` 规则

新增默认忽略：

- `.team/交接箱/**/*.pdf`
- `.team/交接箱/**/样张/*.html`
- `.team/交接箱/**/系统样例/*.html`
- `.team/交接箱/**/连续正文/*.html`
- `jewelry-qms/.team/`

这不会删除任何本地文件，只防止之后误提交。

## 操作口径

- 以后需要提交证据时，优先提交“说明 + 清单 + 哈希”，不直接提交大批样张。
- 需要给人看的样张，用压缩包交付，不和代码提交混在一起。
- 试运行证据只说明 8021 沙箱具备模拟运行基础；纸质体系仍是治理切换完成前的唯一正式体系。
