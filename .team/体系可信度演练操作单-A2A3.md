# A2 备份恢复演练

**目的**：证明"我备份了，且备份能恢复、恢复后数据对"。对应 CL01 7.11.3 b（防篡改丢失）。

**安全前提**：全程用一个叫 `jewelry_qms_drill` 的**临时库**演练。真实的 `jewelry_qms` 库只备份、不动它一根毛。

## 准备（确认系统在跑）

终端里能跑这条，说明系统正常：
```bash
docker compose ps
```
成功标志：`app` 和 `db` 两个服务都显示 running。没在跑就先 `cd jewelry-qms && docker compose up -d`。

## 第 1 步｜备份真实库（2 分钟）

- **做什么**：把真实库导出成一个文件。
- **怎么做**（在 jewelry-qms 目录下）：
```bash
docker compose exec -T db mysqldump -uroot jewelry_qms > "backup-$(date +%Y%m%d).sql"
```
- **怎么算成功**：目录下多了个 `backup-20260710.sql`（或当天日期），文件大小不是 0。打开看一眼，里面是一堆 SQL 语句。
- **卡住**：报错截图发我。

## 第 2 步｜建临时演练库（1 分钟）

- **做什么**：建一个专门用来演练的空库。
```bash
docker compose exec db mysql -uroot -e "CREATE DATABASE IF NOT EXISTS jewelry_qms_drill;"
```
- **成功**：没有报错（建库成功不会输出什么）。

## 第 3 步｜把备份灌进临时库（2 分钟）

- **做什么**：用刚才的备份，在临时库里"复刻"一份真实数据。
```bash
docker compose exec -T db mysql -uroot jewelry_qms_drill < "backup-$(date +%Y%m%d).sql"
```
- **成功**：没有报错。

## 第 4 步｜核对临时库数据（2 分钟）

- **做什么**：抽查临时库里数据齐不齐。
```bash
docker compose exec db mysql -uroot -e "SELECT COUNT(*) AS 记录数 FROM jewelry_qms_drill.record_form_instances;"
docker compose exec db mysql -uroot -e "SELECT COUNT(*) AS 人员数 FROM jewelry_qms_drill.employees;"
```
- **成功**：记录数、人员数和你真实库里的一致（真实库同样查 `jewelry_qms.record_form_instances` 对比）。**这一步证明：备份能完整恢复。**

## 第 5 步｜模拟"丢失"再恢复（3 分钟，关键）

- **做什么**：在临时库里删一条记录（模拟数据丢失），然后从备份再灌一次，看能不能找回来。
```bash
# 先看当前条数
docker compose exec db mysql -uroot -e "SELECT COUNT(*) FROM jewelry_qms_drill.record_form_instances;"
# 删一条
docker compose exec db mysql -uroot -e "DELETE FROM jewelry_qms_drill.record_form_instances LIMIT 1;"
# 确认少了1条
docker compose exec db mysql -uroot -e "SELECT COUNT(*) FROM jewelry_qms_drill.record_form_instances;"
# 从备份恢复
docker compose exec -T db mysql -uroot jewelry_qms_drill < "backup-$(date +%Y%m%d).sql"
# 再数——应该回到原数
docker compose exec db mysql -uroot -e "SELECT COUNT(*) FROM jewelry_qms_drill.record_form_instances;"
```
- **成功**：删之前 N 条 → 删后 N-1 条 → 恢复后又回到 N 条。**这就证明了：哪怕真丢了，备份能救回来。**

## 第 6 步｜销毁临时库（1 分钟）

```bash
docker compose exec db mysql -uroot -e "DROP DATABASE jewelry_qms_drill;"
```
- **成功**：临时库销毁，真实库 `jewelry_qms` 完好（再查一次 `jewelry_qms.record_form_instances` 确认条数没变）。

## 第 7 步｜填演练记录

把下面填好，发给我（我帮你归档进验证方案）：

```

  - employees 条数：备份前 __ / 恢复后 __（应一致）

```

**卡住任何时候**：终端红字截图发我，我判断。最怕的是命令里把 `jewelry_qms_drill` 写成 `jewelry_qms`——**复制粘贴我给的命令，别手敲**。

# A3 权限矩阵测试

**目的**：证明"5 个角色权限对——该看的能看，不该动的动不了"。对应 CL01 7.11.3 a（防未授权访问）。

## 现状

系统现在**只有一个账号 `admin`**（密码 `password`，全员权限）。要测 5 个角色，得先建另 4 个测试账号。

5 个角色：`admin`（系统管理员）、`quality_manager`（质量负责人）、`auditor`（审核员）、`department_head`（部门负责人）、`staff`（员工）。

## 第 1 步｜建 4 个测试账号（10 分钟，用 admin 在系统里建）

1. 用 `admin` / `password` 登录 `http://localhost:8010`。
2. 进**用户管理**，新增 4 个用户，每个绑不同角色：
   - 用户名 `qm_test` → 角色 `quality_manager`
   - 用户名 `auditor_test` → 角色 `auditor`
   - 用户名 `head_test` → 角色 `department_head`
   - 用户名 `staff_test` → 角色 `staff`
   - 密码统一设 `password`
3. **成功**：4 个账号都能建出来。

## 第 2 步｜权限矩阵（逐角色测）

每个账号登录后，按下表试每个功能，记"✅能/❌不能/不该能但能了⚠️"：

| 功能 | admin | quality_manager | auditor | department_head | staff |
|---|---|---|---|---|---|
| 看仪表盘 | ✅应能 | ✅ | ✅ | ✅ | ✅ |
| 看记录列表 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 填写新记录 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 删除记录 | ✅ | ⚠️应不能 | ⚠️应不能 | ⚠️应不能 | ⚠️应不能 |
| 审批/发布文件 | ✅ | ✅ | ⚠️应不能 | ⚠️应不能 | ⚠️应不能 |
| 管用户（建/删账号） | ✅ | ⚠️应不能 | ⚠️应不能 | ⚠️应不能 | ⚠️应不能 |
| 看受控文件 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 改体系文件 | ✅ | ✅ | ⚠️ | ⚠️ | ⚠️ |

> 上表的"应/应不能"是**预期**，基于角色名推断。**实际以你组织授权规则为准**——你觉得某角色该能就能，预期能改。

## 第 3 步｜怎么算成功

- 所有"✅应能"的功能：确实能进/能操作。
- 所有"⚠️应不能"的功能：要么按钮不出现，要么点了报"无权限"。
- **任何"应不能但实际能了"的，是安全漏洞**，记下来要修。

## 卡住怎么办

- 忘了 admin 密码：默认是 `password`，不对的话告诉我，我帮你重置。
- 某角色登录后白屏/报错：截图发我，可能是该角色权限配置缺东西。
- 不确定"某功能该不该给某角色"：对照你们的质量手册岗位职责章节，或问我。
