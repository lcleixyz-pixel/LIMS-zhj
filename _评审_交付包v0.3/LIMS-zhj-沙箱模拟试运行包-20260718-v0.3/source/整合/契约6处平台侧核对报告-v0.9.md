## ② RecordFormRebuildSchema 的列约定(L21)

契约推断:"7 列结构→模板 schema【平台侧核对 RecordFormRebuildSchema 的列约定】"。

实际:
- `record_form_templates.field_schema` 为 JSON 数组,每元素 `{key,label,type,required,[options],[columns],[help_text]}`;type 含 text/textarea/date/person/select/checkbox/signature/repeatable_table/number 等。
- 平台有 `RecordFormRebuildSchema` 命令(`config/console.php` 已注册)+ `database/schemas/record_form_schemas.json`(重建后的权威 schema)+ `record_form_reconstruction_review.json` + `record_form_forward_chain_decisions.json`。
- **"7 列"的真实语义**:`reconstruction_review.field_obligations` 定义 7 个必备字段义务类别——`field_identity / core_record_data / conclusion_or_judgement / responsible_party / date_or_frequency / signature_chain / external_register_boundary`(`schema_coverage.checks` 逐项核验)。这是"7 列约定"的落点,**不是 7 个物理列**。
- 另:`QmsPreimportPackageService::REQUIRED_SCHEMA_KEYS` 定义导入时强校验的 7 个 key:`record_number / record_name / applicable_clause / related_procedure / responsible_position / trigger_time / correction_rule`(与套装 `UNIVERSAL_SCHEMA_FIELDS` 的必填项同源)。

**动作**:契约§一该行写明——"7 列"=`field_obligations` 7 类(覆盖校验)+ 导入强校验 7 个 `REQUIRED_SCHEMA_KEYS`;字段 schema 落 `record_form_templates.field_schema`(JSON),由 `RecordFormRebuildSchema` 命令与 `record_form_schemas.json` 治理。

## ③ P 表({{Pxx}} 参数拍板值)承载位置(L23)

契约推断:"平台配置项/任务调度参数【平台侧核对承载位置】;频次类 P 值应转为定时任务配置(如 P12=每年1次/人→监督任务调度)"。

实际:**平台无单一"P 表/配置表"**,P 值分散承载:
- 方针/目标类(如 P36 质量方针)→ `qms_quality_policies`、`qms_quality_objectives` 两表;
- 频次/提醒类(如 P12 监督频次、内审/管评周期)→ `notifications`/`notification_users` + 迁移 `reminder_notifications` + `CheckReminders` 命令(定时调度);
- 其他参数→散落于各业务表字段(如 `audit_schedules`、`calibrations` 周期字段)。

**动作**:这是真缺口。契约§一该行改写为"P 值无统一落位,分散于 qms_quality_policies/qms_quality_objectives(方针目标)+ reminder_notifications/notifications(频次,经 CheckReminders 调度)+ 各业务表";并在预导入包附《P 值落位表》(契约§二已提及 F 卡落位表,可仿照增 P 值落位表),逐 P 编号指明落点表/字段。或平台侧补一张 `qms_parameter_decisions` 表统一承载(建议,但属平台改动)。

## ④ 现行块格式(L36:"结构化块/ 每文件的块拆分+块级K引用(json 或 md 表)【平台侧核对现行块格式】")

实际:**平台侧的"块"是两张 DB 表,不是文件态 json/md**。
- `qms_document_blocks`:块主记录。关键字段 `stable_key`、`section_number`、`title`、`block_type`(枚举 `section/purpose/scope/responsibility/process_step/control_requirement/record_requirement/form_schema/clause_trace/text`)、`markdown`、`source_locator`、`status`。
- `qms_document_block_links`:块→追溯对象关系。`block_id` 外键到 element/clause/manual_section/procedure_document/record_form_template/position/business_module;`relation_type`(枚举 `basis/implements/mentions/responsible/requires_record/renders_to/supporting`)、`confidence`(枚举 `high/medium/low/review_required`)。
- 套装侧的"块级 K 引用"=`block_links.clause_id`(K卡→`qms_clauses`)+ `relation_type`。

**关键区分**(契约须写清):
- **预导入包内**的"结构化块"表示=CSV(`manual_blocks_preimport.csv` + `structured_documents_preimport.csv`),由 `QmsPreimportPackageService::readCsv` 读入;
- **平台存储**=上述两张 DB 表。
- 契约§二写"json 或 md 表"是甲方侧(套装)的包内表示推断,**与乙方实际 CSV 表示不符**(见下"重大差异")。

**动作**:契约§二"结构化块/"条改写为平台实际 CSV 文件名 + 对应入库的两张表;`relation_confidence`/`link_confidence` 在导入金样中强制 `review_required`(见乙方金样夹具)。

## ⑤ qms_sources 换版状态机(L59:"乙方将对应 qms_sources 置'换版待响应',关联文件标'现行有效存疑'【平台侧核对状态机】")

实际:换版状态机是**两层**:
- `qms_sources.freshness_status` 枚举:`unknown / current / due / obsolete`;`qms_sources.status` 枚举:`draft / published / obsolete`。
- `qms_external_change_events` 表(迁移 20260704):登记换版事件本身,`status` 枚举 `registered / assessing / revising / closed / exempted`,带 `old_source_id↔new_source_id`、`graph_snapshot_hash`、`published_date/effective_date`。

**缺口**:契约的"换版待响应"与"现行有效存疑"**无 1:1 枚举**。最接近的映射:
- "换版待响应" ≈ `qms_external_change_events.status=registered/assessing` 且关联 `qms_sources.freshness_status=due`;
- "现行有效存疑" ≈ `qms_sources.freshness_status=due`(查新到期,现行性存疑);"已废止"=`obsolete`。
- 平台无单一名为"存疑"的状态;文档/结构化文件的 `review_status`(`draft/structured/published/obsolete`)也不含"存疑"档。

**动作**:契约§四该行改用平台真实枚举——"乙方收到换版信号后,在 `qms_external_change_events` 建 `status=registered` 事件,关联 `qms_sources.freshness_status` 置 `due`;关联文件经 `qms_document_block_links.confidence=review_required` 标记复核"。并明确"现行有效存疑"=`freshness_status=due`。

## ⑥ 运行异常导出能力(L61:"导出 json(事件类型/关联要素/证据引用)【平台侧核对导出能力】")

实际:
- **存储层齐**:`capas`、`capa_sources`(CAPA 来源)、`nonconformities`、`customer_complaints`、`compliance_checks`/`compliance_check_results`、`audit_findings` 均在;`qms_external_change_events` 承接外部变更。
- **导出能力现状**:仅有 CSV 导出——视图层 `dashboard/index.html` 有 `/capa/exportCsv`、`/audit_finding/exportCsv`(CSV,非 json);命令层有 `compliance:assess`(`ComplianceAssess`,产出合规就绪度评估,非"运行异常导出")。
- **缺口**:契约§四期望的"导出 json(事件类型/关联要素/证据引用)"给甲方开 CAPA 归因——**无对应的独立 json 导出命令/端点**。

**动作**:二选一——(a) 平台新增 `qms:export-runtime-evidence --json`(按要素/周期筛选,导出 nonconformity/complaint/quality-control-failure + 关联要素 + 证据引用);或 (b) 契约§四改写为"乙方按 capa_sources/nonconformities 现有结构导出,格式由《运行证据导出 schema》单列"。当前倾向 (a),因甲方 CAPA 归因入口需要稳定 json 契约。

## 重大差异(阻塞转正,非 6 处之一)

### 契约§二预导入包格式 vs 平台实际格式

| 契约§二(甲方推断) | 平台实际(`QmsPreimportPackageService::REQUIRED_FILES`) |
|---|---|
| md 目录树:`手册/ 程序/ 记录模板/ 结构化块/ 追溯矩阵.md 事实对照表.md F卡落位表.md 底稿快照/` | **CSV 文件集** + 一个 manifest |
| `manifest.json`(含 suite_version/contract_version/语义签字清单/facts_hash 等) | `preimport_manifest.json`(实际只强校验 `counts` 字段) |
| — | `documents_preimport.csv` / `structured_documents_preimport.csv` / `record_form_templates_preimport.csv` / `traceability_matrix_preimport.csv` / `manual_blocks_preimport.csv` / `external_sources_preimport.csv` |

即:契约§二描述的包格式与平台 `inspect()` 实际读入的格式**不一致**。`scripts/qms_lims_preimport_build.py` 是从"第五版候选修订"md 源生成这套 CSV 的构建器。

**动作(转正必做)**:契约§二整段重写为平台实际 CSV 格式——列明 6 个必备 CSV 文件名 + `preimport_manifest.json` 的 `counts` 契约 + 各 CSV 列约定(尤其 `record_form_templates.field_schema_json` 含 7 个 `REQUIRED_SCHEMA_KEYS`、`traceability_matrix` 的 `human_review_required=yes`/`relation_confidence=review_required`、`manual_blocks.link_confidence=review_required`)。甲方侧套装产物发包前需经 `qms_lims_preimport_build.py` 或等价转换产出该 CSV 包,而非直接发 md 目录树。
